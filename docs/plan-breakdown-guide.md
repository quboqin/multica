# 计划拆解方法：目标如何放进「计划 → 需求 → 任务」三层结构

本文回答一个具体问题：Multica 只有 **计划（Plan）→ 需求（Requirement）→ 任务（Task，可无限嵌套子任务）** 三层，当一个计划内部包含多个目标（如 "APP上线 / Vendor对接 / 研发系统搭建"）时，目标放在哪一层？周（迭代节奏）又放在哪？如何同时满足执行视角（日会/站会过站）和管理视角（每个目标的进展一目了然）？

## 核心结论

1. **不要把"周"当成任何一层的划分维度。** 周是排期属性（时间维度），目标/需求是结构维度（工作分解），两者正交。把需求命名成 "2026/07/06" 会丢掉结构维度：需求本身没有业务语义，无法按目标汇总进展，跨周未完成的工作也没有归属。
2. **不需要新增"目标"实体层。** 三层 + 任务无限嵌套的表达能力已经足够，只需把各层语义整体上移一格。
3. **同一份数据、两个视图。** 管理视角按结构（需求→任务）分组汇总，执行视角按时间（本周截止的子任务）筛选过站。不要为了站会方便去改结构。

## 层级映射

| Multica 层级 | 承载什么 | 粒度要求 |
| --- | --- | --- |
| 计划 | 一个大交付目标（如 "APP上线前完成安卓+iOS上架及全流程跑通"），有唯一负责人 | 季度/大版本级 |
| 需求 | **计划下的一个目标**（APP上线 / Vendor对接 / 研发系统搭建） | 每个计划 2~5 个 |
| 一级任务 | **可独立验收的交付物**（原方法论中的"需求"），如 "iOS App Store 上架审核通过" | 1~2 周工作量，必须写验收标准（DoD） |
| 子任务 | 执行项，有负责人和截止日期 | 1~3 天 |

周不占任何层级，只作为任务/子任务的**截止日期（或迭代字段）**存在。

## 示例拆解

以 "APP上线前完成安卓+iOS上架及全流程跑通 @徐杰(Jim)" 为例：

```text
计划：APP上线前完成安卓+iOS上架及全流程跑通 @徐杰
│
├─ 需求1：APP上线
│   ├─ 任务：iOS App Store 上架审核通过        （截止 2026/07/10）
│   │    ├─ 子任务：提审材料准备（张三，07/07）
│   │    ├─ 子任务：隐私合规检查（李四，07/08）
│   │    └─ 子任务：提审 + 跟进审核（张三，07/09）
│   ├─ 任务：安卓各渠道包上架                  （截止 2026/07/17）
│   └─ 任务：注册登录 + 核心业务全流程回归跑通  （截止 2026/07/17）
│
├─ 需求2：Vendor对接
│   ├─ 任务：数据源对接
│   ├─ 任务：支付通道对接联调
│   └─ 任务：征信接口对接
│
└─ 需求3：研发系统搭建
    ├─ 任务：各系统模块打通（模块间接口联调）
    └─ 任务：业务策略模块上线
```

## 两个视角如何落地

**管理视角（周报 / 向上汇报）**：打开计划，看到的就是 3 个需求（= 3 个目标）。每个需求的进展由下面任务的完成度自动滚动汇总，例如 "APP上线：5 个任务，3 完成、1 进行中、1 风险（iOS 审核延期）"。不需要任何人工同步。

**执行视角（日会 / 站会）**：按 "截止日期在本周" 筛选出所有子任务，按负责人分组过站。看的是 "本周谁在做什么、有没有阻塞"。

**延期处理**：站会后未完成的子任务直接顺延截止日期，任务和需求结构不动。管理侧看到的是 "该任务延期一周"，而不是结构被打乱。

## 使用纪律

- **一级任务必须是可验收的交付物，不是碎活。** "iOS 审核通过" ✅；"改个登录 bug" ❌（放进某个交付物的子任务里）。否则管理视图会被几十个碎任务淹没，汇总失去意义。
- **每个一级任务写清验收标准（DoD）。** 否则 "Vendor对接" 这类工作永远说不清完成没完成。
- **每个任务只归属一个需求（目标）**，避免进展重复计算。

## 为什么不新增"目标"层

- 四层结构（计划→目标→需求→任务）对 2~10 人团队是过度设计。层级越多维护成本越高，最终一定有某一层沦为形式化空挂。Linear 也只有 Project → Issue → Sub-issue 三层。
- "目标"和"需求"本质是同一类东西：都是 "计划下面的一个可汇总的工作块"，区别只在粒度。粒度问题用任务嵌套解决即可，不需要新实体。
- 如果将来某个需求确实过大（下面挂了 30+ 任务看不过来），优先考虑给计划加"分组/里程碑"这类轻量聚合能力，而不是加正式的实体层。
