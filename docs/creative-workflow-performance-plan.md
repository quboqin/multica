# 创意素材协作流程提效方案

更新时间：2026-08-02

## 1. 用户等待口径

性能计时从用户在候选池中完成选图、逐图调整并确认推荐文案，点击“生成修图”开始。爬图、利益点
分析和文案推荐属于生成前的人机协作，不计入本段等待时间。点击生成后，正常流程不再要求用户参与；
每张素材通过 QC 后立即进入父 Issue 结果看板，其余素材继续运行。

## 2. 保留的 Multica 原生协作

工作流继续由普通平台 Skill 描述，Leader 根据 Skill 和本轮已确认输入动态委派，不把 AdaKami、
V01-V03、尺寸数量或市场规则写入底层业务代码。每张素材保留独立工作 Issue，工作 Issue 下保留：

- 创意规划智能体；
- V01、V02、V03 三个修图智能体；
- Prime 包装智能体；
- QC 智能体。

每个智能体仍有原生子 Issue、会话、评论、工具调用、附件、耗时和返工记录。减少的是纯技术尺寸
子 Issue 和没有决策价值的 Leader 重复唤醒，不减少角色协作证据。

Skill 有三层状态：仓库 `SKILL.md` 是版本控制源，工作区 Skill 是平台已发布版本，智能体详情显示
的是该智能体已绑定版本。修改源文件后必须重新发布并绑定；查看本验收工作区全部 Skill 使用
`http://localhost:3000/ad-creative-direct-pilot/skills`，不能只在某一个智能体详情中查找其他角色
的 Skill。

## 3. 图片执行模型

每个创意变体固定采用两个真实图片波次，不假设横版或竖版单次调用更快：

```text
第一轮：生成 1080x1080 方形母版
第二轮：1200x628 横版和 800x1000 竖版同时生成
```

V01-V03 的方形母版并发执行。任一母版完成后，对应修图智能体立即在同一个 Issue 内提交横版和
竖版，不等待 Leader 再次委派。三个尺寸的请求 ID、提示词、耗时和附件全部留在该变体 Issue。

## 4. 通用平台能力

以下能力是跨工作流通用原语，不包含广告业务规则：

- `multica issue create-batch --input-file`：一次创建并分配一组原生子 Issue；
- 子 Issue 完成回执：平台自动唤醒直接父 Issue，Leader 用
  `multica issue children <id> --compact` 只读取直接子项；
- `multica image edit-batch --input-file`：在同一 Agent Issue 内提交多个图片请求；所有 CLI 进程
  共用账号级图片槽位；
- Skill reference：Prime 批量合成、QR 复解码、图片规范化和 QC 批检均由版本化确定性工具完成；
- `multica creative delivery register --input-file`：把候选、变体、尺寸、修订、底图、Prime 和 QC
  证据登记到父 Issue 结果看板。

Leader 在每轮开始时根据自然语言 Skill 生成委派清单。平台通用代码只负责 Issue、批量命令、全局
并发、附件和交付登记；业务以后调整变体数、尺寸、市场包或验收要求时修改平台 Skill 和资源，
不修改底层业务代码。

## 5. 需要实施的优化

1. 用户点击生成时冻结素材、利益点、文案、市场包、资源和 Skill 版本，后续不重复分析。
2. Leader 一次委派所有已满足依赖的任务；子 Issue 完成会唤醒 Leader，但未满足下个依赖时立即退出。
3. 每张素材的 V01-V03 同时开始方形母版；母版完成后横版与竖版立即并发。
4. 图片调度优先执行能够关闭一个变体或一张素材的尾部任务，避免最后一张图独占完整波次。
5. Prime 每张素材保留一个 Agent Issue，九张图使用通用合成工具批量包装。
6. QC 每张素材保留一个 Agent Issue，确定性检查批量执行，语义检查一次读取九张图。
7. 返工只重做失败尺寸；同一 QC 的多个失败项先按变体聚合，恢复后只创建一个变更子集 Prime 和
   一个变更子集 QC，已通过产物直接复用。
8. 每张素材 QC 通过后立即写入结果看板，Leader 在全部完成后发布最终汇总。

## 6. 当前基线

- 图片模型：`gpt-image-2`；
- 图片接口：daemon 配置的 `/images/edits`；
- 当前实测图片 provider 单次请求：约 74-140 秒；
- 图像编辑智能体并发：5；
- daemon 总任务并发：8；
- 已有五路真实图片任务同时运行且未触发 429；
- 优化前单素材 3 x 3 实测为 61-88 分钟；ADC-202 优化后无返工正常路径的阶段实测支持
  26-30 分钟区间，完整现场因首次发现 provider 竖版比例漂移、QC manifest 兼容和真实安全区碰撞而
  包含额外修复时间，不能把现场总墙钟冒充正常路径。

## 7. 并发验收结果

使用与生产一致的 `multica image edit`、相同 provider 和同一张低复杂度参考图，关闭自动重试后同时
提交 8 个请求。2026-08-02 实测结果：

- 6 路成功，0 路超时，0 路 5xx；
- 第 7、8 路在约 31 秒返回 HTTP 429，错误为用户并发上限超出；
- 6 路成功请求在约 74-127 秒内完成，本轮墙钟为 127.9 秒；
- 成功 request ID：`d6c11b2f-2fda-4420-94be-9010e10b0e00`、
  `451c8964-950e-4067-af9c-38b39d35bf24`、`a3906a8d-779f-46cf-bce2-641f46408805`、
  `b55236d1-6063-4eb3-858e-e03a59b11dd6`、`01a03d3f-8dc4-47d3-8fff-fb126143cdaa`、
  `685da6bc-7770-41fa-a7ea-ed7bd758b7a8`；
- 429 request ID：`949bf4b5-9b9b-42e6-b6a0-5e8ba89b59a2`、
  `7cf844c1-fa05-4123-9c6d-6413b8209b73`。

这次探测证明当前账号的图片 provider 硬并发上限为 6。低复杂度探测图只用于判断请求是否被真正
并发接收；ADC-202 的真实生成和恢复调用进一步确认生产请求也在约 80-140 秒完成。测试图片不进入素材库或
结果看板。后续额度变化时可复用 `scripts/test-image-provider-concurrency.ps1`，脚本只从本机 DPAPI
密文读取密钥，输出汇总和 request ID，不输出密钥。

## 8. 生产并发配置

- provider 硬上限：6；
- 图像编辑智能体：维持 5，给人工微调、失败重试或同账号其他图片任务保留 1 路；
- daemon 总并发：维持 8；五路图片运行时仍可运行 Leader、Prime 或 QC，避免文本智能体无限堆积；
- 素材小队 Leader：3，以批量委派和幂等检查吸收并发完成回执；
- 生成方案智能体：3；Prime 包装智能体：4；广告验收智能体：3；广告参考分析智能体：4；
  AppGrowing 素材采集智能体：2。

各智能体上限不是预留槽位，实际同时运行数仍受 daemon 的 8 路总上限约束。只有图像编辑智能体
占用图片 provider 的 6 路额度；本机已确认图片编辑凭证与 Codex 文本智能体登录凭证不同，其他
角色不会消耗本次测得的图片额度。静态配置不建议把图像编辑直接设为 6，否则人工精确调整、另一批
素材或自动重试会立刻遇到 429。以后平台具备按 provider 账户统一调度的动态信号量后，可以在确认
没有其他图片请求时短时吃满 6 路。

## 9. 一至三张素材的等待时间

以下时间从用户确认逐图文案并点击“生成修图”开始，到全部素材进入结果看板结束。每张素材都是
3 个创意变体 x 3 个尺寸，共 9 次图片生成。区间以 ADC-202 的方案、三变体、九图 Prime、九图 QC
实测和五图片槽位排队模型估算，不含质量返工：

| 入选素材 | 最终成图 | 正常整批墙钟 | 平均每素材 |
| --- | ---: | ---: | ---: |
| 1 张 | 9 | 26-30 分钟 | 26-30 分钟 |
| 2 张 | 18 | 32-40 分钟 | 16-20 分钟 |
| 3 张 | 27 | 38-50 分钟 | 13-17 分钟 |

多选后平均每张素材会变短，因为方案、图片波次、Prime 和 QC 可以跨素材重叠执行；但用户等待的是
最后一张完成的墙钟时间，不应把“平均每素材”误报成整批交付时间。任一尺寸需要一次真实模型返工时，
单项通常增加 5-8 分钟；同一 QC 的多个返工按变体并发时，ADC-202 七张恢复实测墙钟为 9分46秒，
而不是七项串行累加。每张素材通过 QC 后应立即出现在结果看板，
不必等整批结束。

未来图片硬并发提高到 8 时，主要缩短多素材的图片排队，方案、Agent 准备、Prime、QC 和发布不会
同比缩短。按当前 80-140 秒图片调用估算，1 张只能再省约 1-3 分钟，2 张约省 3-6 分钟，3 张约省
6-10 分钟。没有账号级动态调度前仍使用 5，避免人工微调、另一批素材或自动重试撞满额度。

## 10. ADC-202 提效现场

验收入口为父 Issue `ADC-201`，创意工作 Issue 为 `ADC-202`，候选为真实归档素材
`65c98abc-33cc-4156-8b60-12b064024a12`。正常阶段实测：

- 方案 `ADC-206`：4分10秒，上一版约 7分30秒；
- 三个变体同秒启动，首轮无品牌图在约 12-14 分钟内产出；
- 九图 Prime `ADC-210`：2分34秒，上一版约 5分37秒；
- 修复契约后的九图 QC 机器检查与视觉复核：约 2分29秒，上一版约 10分10秒；
- 真正发现 7 张左上品牌碰撞后，Leader 没有创建 7 条流水线，而是创建 V01/V02/V03 三个恢复
  Issue；7 次真实图片调用在 5 槽下墙钟 9分46秒；
- 七图恢复 Prime `ADC-217`：3分57秒，其中包含一次已修复的并行下载目录竞态。
- 七图恢复 QC `ADC-218`：3分30秒，机器检查 7/7、视觉检查 7/7 通过；
- Leader 最终发布：3分43秒，父 Issue `ADC-201` 最终具有 9 张附件和 9 个不重复的
  “V01-V03 × 三尺寸”结构化交付键。

现场还首次验证了两个异常边界：provider 偶发把 4:5 竖图返回为近 2:3 时，先请求 1024x1280、
再请求 1280x1600，两次均失败才允许使用保留完整内容的边缘淡化延展；QC 直接读取 Prime 原生
manifest 和 compose result，不再创建证据修复/复验 Issue。稳定路径预计 26-30 分钟，但需要再跑
一套没有现场改 Skill 的冷启动样例，才能把该区间升级为完整端到端实测结论。

本次从修正后正式启动 `11:24:54 UTC` 到发布完成 `13:09:00 UTC` 共 1小时44分06秒。这个墙钟包含
现场定位比例漂移、修改规范化策略、修复 QC manifest 契约、处理真实安全区失败和重新部署 Skill，
不能用于表示修复后的正常生产耗时。恢复阶段从三个修图 Issue 同时启动到最终发布共 23分14秒；
其中七次真实图片编辑的核心墙钟为 9分46秒，已直接证明五槽并发和恢复聚合生效。

## 11. 早期质检收敛策略

性能基线只统计正常路径。Prime 空间判定现只使用市场包实际 `hard_regions`，顶部/底部上下文切片
为非阻断软引导；质量警告不再触发自动图片返工。硬失败只包括文件/尺寸/包装/二维码错误、Prime
资产缺失或不可读、竞品残留、获批金融事实或 `must_preserve` 被删改/实际遮挡，以及严重破图。

这项调整不把质量问题藏起来：QC 仍逐图输出 `quality_warnings` 并发布到结果看板，用户可直接用
自然语言发起精确调整。它避免在初版规则尚未积累足够坏样本时，因为一般构图差异反复消耗图片
调用。后续从看板反馈和不满意成图中归纳稳定模式，再把确认过的模式提升为硬规则。
