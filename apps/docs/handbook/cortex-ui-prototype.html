为什么不给新对象建新的顶层导航

main 把工作对象和 AI 团队分组，把统计与设置放在底部。提案沿用这个结构，跨对象入口继续走搜索（⌘K）与固定。 当前固定区支持视图、issue、项目（app-sidebar.tsx 的 pin 逻辑）；新增文档与表格仍需扩展对象类型、路由与访问校验，不能仅凭视觉复用视为已支持。

文档与表格：侧栏不展开，各开一列

侧栏里「文档」「表格」各只有一个入口，不在侧栏内就地展开成树或列表。点击后在侧栏右侧新增一列： 文档页是 文档树（搜索、筛选、新建、拖拽调序），表格页是 表格列表（搜索、新建、记录数）。 两列互不混排 —— 文档页不出现表格列表，表格页不出现文档树（见 S2–S6）。 侧栏在 xl 以下自动收起时第二列保留，列顶的按钮可重新打开侧栏；md 以下只容纳一列：文档 / 表格首页显示这一列，打开具体对象后由内容取代。

共享视图栏是 FR-002 的验收面

右上角的 DataSource: issue 在原型里是显式可见的，正式版应移除。它在这里的作用是让评审者一眼确认： S1 与 S4 表达拟议的同一套视图栏契约；本 HTML 是两处静态示意，并未实现共享 React 组件。 不同数据源通过能力声明决定可用过滤、分组、排序与写回；验收还需覆盖服务端分页、工作区隔离、Query 缓存与 WebSocket 协调。
  • 既有布局 5 种（ViewMode = board | list | table | gantt | swimlane，源自 packages/core/issues/stores/view-store.ts）保持原样
  • 新增 2 种：日历 FR-004、画廊 FR-005，用蓝点标记

列表里多出来的一列：kind 徽章 FR-011

引入 issue.kind 后，同一个列表里会同时出现任务 / 文档 / 知识候选 / 流程实例。 设计上必须让它们可区分但不喧宾夺主 —— 用 11px 徽章而不是图标或颜色底纹， 并在视图栏第一个过滤 chip 固定为「类型」，默认值 全部。

需要你确认的产品判断：默认值应该是「全部」还是「仅任务」？ 我倾向 全部（否则文档永远不会被偶遇），但这会改变所有老用户的默认列表内容。

刻意没有出现在这个列表里的东西：record

表格的行（record）不进 issue 列表、不进收件箱、不占用 MAGI- 编号序列 —— 这是 D-1 决策的直接后果，也是 FR-024 的验收标准之一。 建 1000 行 record 后，这一页应当没有任何变化。

为什么内嵌块要显式露出 Markdown 串

平台以 Markdown 作为存储与交换格式，编辑器已有 !file[名称](url) 这一自定义语法先例 （packages/views/editor/extensions/file-card.tsx，带双向 roundtrip 测试）。 collection-view 块沿用同一前缀风格 FR-033， 在原型里把序列化结果印在块底部，是为了让评审者确认：这块东西经过 Markdown 往返不会丢， 在 CLI、agent 上下文、纯文本客户端里降级为一个普通链接而不是乱码。正式版这一行应默认隐藏。

「实时」这个词在这里只指数据，不指协同

绿点表示嵌入的是 linked view（视图 ID + 本地覆盖），源表变了这里就变 FR-034。 它不表示多人实时协同编辑 —— 一期明确不做 NG-2 / A-1。 这两件事在界面上极易被用户混淆，所以正文区不使用任何「其他人的光标」类视觉语言， 一期必须具备整篇文档 revision 冲突检测、保留本地草稿和显式解决入口 FR-017；段落占用提示 FR-017A 与版本历史 FR-018 单独排期。当前 description 的 last-write-wins 不能满足这项验收。

文档正文的智能体 mention 在本提案中只作引用，不承诺执行；评论按现有路由、权限与触发规则处理，/note 不触发该评论执行路径。

本轮新增：内嵌块的写回必须复用既有的运行确认

改 record 只是改数据；改 issue 会触发平台行为。在这个块里把一张 issue 卡片拖到「进行中」， 可能唤醒一个 agent、关闭一个 stage barrier、往别人收件箱里塞一条。

好消息是平台已经解过一次这道题：表格视图里把 agent 负责的 issue 从 backlog 改成 todo 时， 不直接应用，而是弹一个运行确认框。内嵌块必须复用这个机制，而不是另写一套写回 —— 见 FR-032、验收 AC-14。

另加一条一次性提示：首次在内嵌块里编辑时提示「这条修改会写回源表『需求池』，另有 2 篇文档正在引用它」，之后不再出现。 Notion 老用户知道 database view 是活的，新用户第一反应一定是「我只是在这篇文档里改改」。

右栏第二个 tab 是这次设计里最容易被砍、但最不该砍的东西

「反向引用」把 FR-036 从一个删除确认弹窗提升成常驻面板。 理由：一旦表格可以被 N 篇文档以不同过滤条件嵌入，「这张表还有谁在用」就成了删除、改字段、改选项之前的必查项。 Notion 在这件事上做得很差（引用关系不可见），是可以直接拿来做差异化的点。

本轮修订：status 与 assignee 都不隐藏，「kind-aware」= 换措辞而非藏字段

提议将 draft / reviewing / published 分别映射到生命周期 unstarted / started / done FR-016。 main 的完整分类为 unstarted / started / done / closed；自定义状态仅继承生命周期，不自动继承 backlog 停放、in_review 审核或 in_progress 恢复行为。 旧 category 字符串仍在 API 边界兼容解析，但不提供旧行为保证（server/internal/issuestatus/issuestatus.go）。

状态位于标题上方，显示文档状态目录里的名称。负责人代表内容责任人；文档审核、发布和通知仍需明确产品契约。

选择智能体负责人可能触发运行，不能承诺立即启动。复用运行确认与服务端预览，展示权限、触发策略、Triage、排队和运行时结果。待分拣任务会阻止从任务派生的执行；自定义 draft 也不自动成为 backlog 停放区。

S3 · 插入路径：/view 走现有斜杠命令，不新建入口

编辑器已有斜杠命令扩展（packages/views/editor/extensions/slash-command-extension.ts）， 插入活视图只是往这个列表里加一项。左图是命令面板，右图是选中后弹出的数据源选择器 —— 这一步是产品分叉点：默认给「活视图」还是「静态快照」。

「静态快照」被刻意做成禁用态，而不是不出现

用户会找它 —— 从 Notion / 飞书迁移过来的人第一反应就是「我只想贴一份当时的数据」。 如果直接不给，他们会去截图；给了，则每一份快照都会立刻过期，成为文档里的假事实。 设计上的处理是：把选项显示为禁用，并在旁边给出替代路径（活视图 + 本地过滤锁定某个时间字段）。

这是一条需要你拍板的产品取舍，不是纯 UI 问题。我的建议是一期不做快照。

「新建表并嵌入」是这一屏里最重要的一条

它把建表的入口从「先去表格页建好、配好字段、再回文档引用」压缩成一步。 Notion 的核心增长路径正是这条 —— 用户在写东西的过程中顺手建了数据库。 对我们来说它还有额外价值：新表默认落在当前 project 下，避免 workspace 级表格野蛮生长。

「任务（内置集合）」出现在数据源列表里

这一条不是凑数：它是共享引擎层在用户面前的第一次显形 —— issue 只是一个内置集合，所以它当然也能被嵌进文档 FR-002。 「在周报里嵌一个本周 issue 看板」是这套架构几乎免费得到的能力，而且是日常最高频的用法。

权限在这一步就要处理，不能推到渲染时

选择器只列出当前用户可见的表与视图（含 private 视图仅自己可见）。 但文档会被分享给更多人 —— 所以插入时需要提示：「本文的 3 位协作者中有 1 人无权访问该表，他们看到的将是占位块」。 一期若不做记录级权限 A-2，这个提示只需按表级可见性计算，成本很低，但能避免最尴尬的一类事故。

选择器的无障碍交付契约

列表里的删除：藏在「···」里，确认后才执行

文档树和表格列表的每一行，悬停或键盘聚焦时才出现行内操作（文档：收藏 / 添加子页 / ···；表格：记录数让位给 ···）， 平时不占宽度，窄列里的标题才放得下；触屏设备没有悬停，始终显示。菜单打开时触发按钮保持可见。

「删除」是菜单里唯一的红色项，点击后弹确认框：标题写出对象名，正文只写后果 —— 文档的子页 不会一起删，服务端把它们移到根层级，所以有子页时多写一行； 表格的删除在服务端是归档（archived_at），但目前没有恢复入口，确认框如实写「不可撤销」， 左栏的「已归档」与恢复仍是提案，做出来以后再改文案。

确认框在服务端返回前保持打开并禁用按钮（「删除中…」）；失败时保留对话框并提示错误； 删的是当前打开的那一项，成功后回到文档 / 表格首页。 权限：文档与任务一致，成员都可删；表格只有创建者和 workspace 的 owner / admin 能看到「···」，与服务端判权一致。

添加 / 修改字段用同一个面板，锚在表头上

参考飞书多维表格：表头最后一格是 +，紧跟在最后一个字段后面（还没有字段时直接写成「+ 新建字段」）；点它在正下方弹出字段面板 —— 名称、字段类型（类型列表从面板侧面展开），单选 / 多选再多一段 选项（颜色、名称、增删），底部是配额与 取消 / 创建字段。 Enter 提交，Esc 或点面板外取消，保存失败时面板不关并显示服务端错误。 修改字段从表头菜单的「修改字段」进入同一个面板，锚在那一列表头下，主按钮为 保存；类型只列安全转换，删除选项会在保存前提示将清空哪些记录。 新建的表只有「名称」一列（记录标题，不可删、不算字段配额），因此 + 必须一眼可见，不再用居中弹窗。

本期不做：默认值、字段捷径、AI 字段、关联 / 查找引用 —— 服务端暂无对应能力，面板里不放占位控件。

首列是记录标题：能改名，别的都不能动

每张表的第一列显示记录标题（record.title），它不是字段目录里的字段：不能隐藏、归档、分组、换类型，也不占字段配额。 但列名必须能改 —— 「名称」对客户表、设备表都不贴切。表头与其他列一样是菜单：修改字段（右侧标「文本」）、升序、降序； 「修改字段」打开同一个面板，锚在首列下：名称可改，类型下拉禁用并写明原因，没有配额行。

整个表头格都是菜单的点击区，不只是左侧那几个字：首列很宽而列名很短，只认文字的话，点在空白处毫无反应， 用户会以为这一列不能改。悬停时整格变色并在右端出现下拉箭头；拖动手柄和列宽分隔线照旧。 「显示」的字段列表也把首列排在第一行（始终显示，不可勾选），右侧同样有铅笔 —— 改首列不必依赖表头。

列名存在表上（collection.title_name）。留空或改回默认名 = 不存，继续跟随界面语言显示「名称 / Name」； 排序菜单里的首列也用这个名字。只有表格管理者（创建者、owner、admin）能看到「修改字段」。

没有表头的布局，也要能加 / 改字段

布局是浏览器里记住的偏好：一张表上次停在「看板」，下次打开还是看板。看板、日历、画廊都没有表头， 于是表头上的 + 和列菜单都不在了 —— 没有单选字段的看板只剩一句「请添加单选字段」，用户无处下手。

两处补齐：① 空状态给出缺的那个字段 —— 「新建字段」按钮直接打开字段面板，类型预选为单选（看板）或日期（日历）； ② 「显示」就是字段配置 —— 每个字段右侧一支铅笔打开修改面板，列表底部「+ 新建字段」，面板锚在「显示」按钮下。 日历没有可显隐的内容，管理者看到的是同一个入口、名为「字段」的纯列表。非管理者看不到这些入口。

字段菜单底部那行配额说明是有意加的

现有实现里，字段目录是 workspace 全局、活跃定义上限 20（191_issue_properties.up.sql 的注释与 handler 校验）。 用户完全不知道这个上限的存在，直到某天建不出新字段。 新的 collection 字段目录每表独立、建议上限 50 FR-022 —— 把两个配额同时印在菜单里，是让用户一眼理解「表格的字段不会挤占工单的字段」，这正是方案 C 分层的用户可感收益。

两种 relation 在视觉上必须可区分

「关联任务」指向 issue（record_link.to_type='issue'），用蓝色带 issue 图标的 chip； 「提出客户」指向另一张表，用中性灰 chip FR-028。 理由：指向 issue 的关联会把用户带出数据世界、进入有状态与负责人的工作世界，这是一次上下文切换，值得一个独立的视觉信号。 最后一行故意留了一个失效关联（已删除 删除线）—— 关联边保留但标记失效，不静默消失。

本轮修正：这一列只能放人，不能放 agent

「负责人」是 actor 类型字段，而现状 actorPropertyKinds 只有 member —— actor 字段今天填不了 agent，也填不了小队。 v0.1 的这一屏画错了（有一行放了 agent 头像），已改为成员。

member: 前缀提供类型扩展位置，但扩展到私有智能体仍需写入权限、成员可见性和 facet 查询防泄漏校验；并非只放宽前缀。 而 record 没有 assignee 语义（D-1），actor 属性是它唯一能表达「谁负责」的手段。 collection 是否支持 member / agent / squad 仍见 Q-U3；还需独立定义集合字段管理权限，不能绕过当前 issue 字段管理对智能体的限制。

「归档字段」不是「删除字段」

沿用平台既有策略（定义只归档、不物理删除，历史值保持可解析）。 菜单里把这一项标红但写明「不删数据」，避免用户为了「彻底删掉」去反复找别的入口。 字段类型变更同理：只允许安全方向转换，不安全的转换要求新建字段 + 迁移。

底部那行 回收站 6（保留 30 天） 是 record 与 issue 的一处关键差异

issue 走的是状态流转（cancelled 仍在系统里）；record 走的是软删除 + 回收站 FR-024。 表格用户的心智模型是 Excel，删行就该进回收站；工单用户的心智模型是工作流，取消不等于删除。 两种模型不能互相污染，所以两者的删除入口、文案、恢复路径必须显式不同。

S5 · 同一份数据的四种布局，其中两种是新增

看板 / 表格 / 甘特 / 泳道复用现有实现，日历 FR-004 与画廊 FR-005 是本期新增， 且必须 issue 与 collection 双源验收 —— 只在其中一边能跑就说明没接在共享引擎上。

本轮新增：模板必须指定 runner，不允许为空

阶段屏障的真实语义比看上去弱：服务端只检测到屏障关闭、唤醒父 issue 的负责人， 它不会把下一阶段的子 issue 从 backlog 提成 todo；而且父负责人是人类时，这条唤醒通知根本不发送。

所以「运行一次」编译出的父 issue 必须挂一个 agent 或小队当推进者。 这不是可选项 —— 缺了它，流程跑完第一阶段就停住，而且极难排查，因为每个子 issue 看上去都正常完成了。 见 FR-052、验收 AC-11。

画布上没有条件分支的连线样式，这是有意的

条件分支与循环是二期 FR-055。如果一期就在画布上画出带条件的边，用户会立刻去用， 然后发现求值不生效。能力没做，界面就不要暗示它存在。 一期的表达力边界是：阶段屏障 + 依赖边 + 自定义状态 —— 足够覆盖绝大多数审批流与评审流。

「从已有 issue 链反向生成」是冷启动的关键入口

没人愿意对着空画布画流程。而工作区里已经跑过的 issue 链就是现成的流程实例， 把它反向抽成模板 FR-053，用户的第一个模板成本接近零。 这条路径也顺带解决了「模板市场」FR-056 在一期缺位的问题。

顶部那条绿色状态带在后端不可用时会变成黄色，且必须留在原位

7.5 规定：知识库后端不可用时 knowledge.search 快速失败并降级到平台自带全文搜索，不阻塞 agent 运行。 界面上的对应表达是：状态带原地变黄、写明「已降级为全文检索」，而不是弹一个错误对话框。 弹窗会让用户以为整个系统坏了；状态带只是告诉他检索质量下降了。

第三条候选是我特意放进原型的

它低置信度、与既有条目冲突、而且结论一旦入库会污染后续所有 agent 的推理。 它的动作按钮没有「入库」，只有「丢弃」和「升级为 issue 去核实」。 记忆晋升最大的风险不是漏掉知识，而是把没验证的推断固化成事实 —— 界面必须让高风险条目走不通「一键入库」这条路。

本轮新增：第二条状态带是为了让一类静默故障可见

remote-mcp-v1 是「remote-MCP 类 plugin 能否投递到某台 daemon」的开关，判定失败即关闭。 用户机器上的 daemon 版本过旧、不声明该能力时，知识库工具不会被投递，而且是静默的 —— agent 不报错，它只是手里没有那几个工具，然后照常回答，答案里没有任何知识库内容。

排查这种故障非常痛苦，因为每一层看起来都正常：plugin 装好了、后端连通了、agent 也跑了。 所以把它做成一条常驻状态带，而不是留在日志里。见 FR-048、验收 AC-P8。

置信度条是提炼 agent 给的，不是真值

正式版应在旁边给出它的计算口径（来源数量 / 是否被多次独立提及 / 是否与既有条目冲突）， 否则用户会把它当成系统对内容正确性的背书。 这一条在 PRD 里还没有对应需求 —— 建议补一条 FR：候选条目必须携带可解释的来源链，界面上一键可展开。

「语料来源」在侧栏里是一个独立入口

FR-045 让已发布文档与表格快照自动成为语料。用户必须能回答「知识库里到底有什么、从哪来的」， 否则自托管带来的信任优势会被「黑箱」感抵消 —— 这正是 Notion AI 当前最被诟病的一点。

v0.4 保留并校正的设计约束

以下约束在 2026-09-18 对照 main 复核；实际验收以配套 PRD 的当前契约为准：
  • workflow 模板必须指定 runner（S7）—— 服务端只唤醒不推进，缺了它流程会静默停住
  • 内嵌块写回复用 issue-run-confirm（S2）—— 改 issue 有副作用，平台已有确认机制可复用
  • 内嵌块首次编辑给一次性提示（S2）—— 说清「改的是源表，另有 N 篇文档在引用」
  • actor 字段今天只能填人（S4）—— v0.1 画错了，已修正；是否给 collection 开到 agent / squad 待拍板
  • 知识库设置页显示 daemon 能力覆盖（S8）—— 让一类静默故障可见
  • 语料入库新增 knowledge_ingest 投递层 —— 照搬 webhook 的幂等 + 租约 + 可重放模式
  • 文档的 status 与 assignee 都不隐藏（S2）—— 「kind-aware」从「藏字段」改为「换措辞」
tint 色阶仍待设计与对比度评审，不属于已存在的共享 token。

交付范围与后续设计

  • 移动端。一期范围为 Web / Desktop；窄屏阅读适配不是原生 Mobile 验收。apps/mobile 拥有独立 UI、数据层与构建，文档编辑、表格与画布另行设计和立项。
  • 权限的界面表达。一期不做记录级 / 字段级权限 A-2，因此原型里没有任何权限控件。若定位是可售卖多租户，这一屏要重画。
  • 空状态与首次使用。四个新对象各需要一套空状态和引导，本轮未做 —— 这是决定新功能能否被用起来的关键一环，建议单独排一轮。
