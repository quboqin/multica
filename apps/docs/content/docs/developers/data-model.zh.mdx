Multica 的全部数据存放在 PostgreSQL 17 中，由 sqlc 建模，表数量远超一百张。最重要的一条设计决定：**整库没有一个外键**——关系、校验、级联清理全部由应用层显式完成。下面的 ER 图里所有连线都是虚线，提醒你它们是「应用层约定」而非数据库约束。

本页与[架构内幕](/developers/architecture-internals)和[认证与权限](/developers/auth-and-permissions)配套阅读。

## 建模约定

| 约定 | 做法 | 备注 |
| --- | --- | --- |
| **无外键** | 禁止 `FOREIGN KEY` / 级联删除；依赖清理放进应用事务（如删成员时同一事务内下线 runtime、归档 agent、取消任务、删 token） | 迁移 lint 测试强制执行 |
| **主键** | 统一 `UUID DEFAULT gen_random_uuid()` | 少数例外：GitHub 待领安装以平台数字 ID（`BIGINT`）作 PK、渠道绑定令牌以 `token_hash` 作 PK、若干汇总表只有复合唯一索引 |
| **租户边界** | 几乎每张表都带 `workspace_id`，所有查询按它过滤 | 它同时是权限边界与索引前缀 |
| **人读 ID** | issue 编号 = `workspace.issue_prefix + '-' + issue.number`（如 `MUL-4302`） | 计数器是 `workspace.issue_counter` 行内自增，配 `UNIQUE(workspace_id, number)`，每个工作区从头计数 |
| **排序** | `position DOUBLE PRECISION` 分数排序（issue、pinned_item、issue_status、issue_property…） | 拖拽插入无需重排整表 |
| **乐观并发** | `revision BIGINT`（issue、comment）+ 请求携带 `expected_revision` | 渠道会话绑定另有 `route_revision` / `context_revision` |
| **「软删」** | 全库没有 `deleted_at`；用语义化字段：`archived_at`（agent、squad）、`status='archived'`（chat、autopilot）、`revoked`（PAT）、`is_active`（分享链接）… | 删除要么是真删（应用事务清理），要么是语义归档 |
| **时间** | 一律 `TIMESTAMPTZ DEFAULT now()`；仅 issue / project 的起止日期与用量日表用 `DATE` | 汇总按 UTC 物化，`user.timezone` 只影响渲染 |
| **JSONB** | `issue.metadata` ≤ 8 KB、`issue.properties` ≤ 16 KB（`CHECK` 限长 + GIN `jsonb_path_ops`）；配置类字段广泛使用 JSONB | `properties` 的键是 `issue_property.id`，值类型由属性定义决定 |
| **租约 / Outbox** | `lease_token + lease_expires_at + next_attempt_at + attempt + dead_lettered_at` 模式反复出现 | webhook_delivery、seat_capacity_outbox、channel_media_pending_object、sys_cron_executions… |
| **迁移纪律** | 索引必须 `CREATE INDEX CONCURRENTLY` 且单文件单语句；新 `CHECK` 先 `NOT VALID` 再补 `VALIDATE`；条件跳过的迁移要求后续 DDL 幂等 | 迁移执行器在事务外跑文件，因此 migrations 目录里有大量单条索引文件 |

## 多态关系总表

没有外键的另一面是多态关系用得非常自由——「判别列 + ID 列」是全库最高频的建模手势，agent 借此在每个协作场景与人类同权出现：

| 表 · 判别列 | 可指向 | 语义 |
| --- | --- | --- |
| `issue.assignee_type` | `member \| agent` | 核心多态：任务指派给人或 agent |
| `issue.creator_type` / `project.lead_type` | `member \| agent` | 创建者 / 项目负责人 |
| `comment.author_type` | `member \| agent \| system \| plugin` | 四类评论作者，编辑权按 (type, id) 精确匹配 |
| `inbox_item.recipient_type` · `.actor_type` | `member \| agent`（actor 另含 `system`） | 通知的收件人与动作者都可是 agent |
| `issue_subscriber.user_type` / reactions 的 `actor_type` | `member \| agent` | 订阅与表情 |
| `attachment.uploader_type` | `member \| agent` | 附件上传者；挂载点为六个可空列 |
| `squad_member.member_type` | `agent \| member` | 人机混编小队 |
| `autopilot.assignee_type` / `quick_action.assignee_type` | `agent \| squad` | 自动化的执行者是 agent 或小队（不能是人） |
| `agent_invocation_target.target_type` | `workspace \| member \| team`（保留） | 调用白名单的授权对象 |
| `pinned_item.item_type` | `issue \| project \| view` | 个人置顶 |
| `issue_label.resource_type` | `issue \| agent \| skill` | 一套标签服务三种资源，各有关联表 |
| `agent_task_queue.trigger_evidence_kind` | `comment \| issue_assignment \| autopilot_run \| rule_version \| rerun …` | 触发证据指针，free TEXT 便于扩展 |
| `plugin_storage.scope_type` | `workspace \| user` | 插件 KV 的作用域 |
