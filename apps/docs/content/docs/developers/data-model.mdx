Multica stores everything in PostgreSQL 17, modeled through sqlc in well over a hundred tables. The single most important design decision: **there is not one foreign key in the database.** Relations, validation, and cascading cleanup are all performed explicitly in application code. Every line in the ER diagrams below is dashed as a reminder that it is an application-level convention, not a database constraint.

This page pairs with [Architecture internals](/developers/architecture-internals) and [Authentication and permissions](/developers/auth-and-permissions).

## Modeling conventions

| Convention | Practice | Notes |
| --- | --- | --- |
| **No foreign keys** | `FOREIGN KEY` and cascading deletes are forbidden; dependent cleanup runs inside an application transaction (removing a member takes its runtimes offline, archives its agents, cancels its tasks, and deletes its tokens in one transaction) | Enforced by a migration lint test |
| **Primary keys** | `UUID DEFAULT gen_random_uuid()` everywhere | Exceptions: pending GitHub installations use the platform's numeric ID (`BIGINT`), channel binding tokens use `token_hash`, and a few rollup tables only carry a composite unique index |
| **Tenant boundary** | Almost every table carries `workspace_id`, and every query filters by it | It is also the permission boundary and the index prefix |
| **Human-readable IDs** | Issue identifier = `workspace.issue_prefix + '-' + issue.number` (for example `MUL-4302`) | The counter is `workspace.issue_counter`, incremented in-row, with `UNIQUE(workspace_id, number)`; each workspace counts from one |
| **Ordering** | `position DOUBLE PRECISION` fractional ordering (issue, pinned_item, issue_status, issue_property, …) | Drag-and-drop inserts never reorder the whole table |
| **Optimistic concurrency** | `revision BIGINT` (issue, comment) plus `expected_revision` on the request | Channel session bindings carry their own `route_revision` / `context_revision` |
| **"Soft delete"** | There is no `deleted_at` anywhere; semantic fields are used instead: `archived_at` (agent, squad), `status='archived'` (chat, autopilot), `revoked` (PAT), `is_active` (share link) | Deletion is either a real delete inside a cleanup transaction, or a semantic archive |
| **Time** | `TIMESTAMPTZ DEFAULT now()` everywhere; only issue and project start / due dates and daily usage tables use `DATE` | Rollups materialise in UTC; `user.timezone` only affects rendering |
| **JSONB** | `issue.metadata` ≤ 8 KB and `issue.properties` ≤ 16 KB (`CHECK` length limits plus GIN `jsonb_path_ops`); configuration fields use JSONB widely | Keys of `properties` are `issue_property.id` values; the value type comes from the property definition |
| **Lease / outbox** | The `lease_token + lease_expires_at + next_attempt_at + attempt + dead_lettered_at` pattern recurs | webhook_delivery, seat_capacity_outbox, channel_media_pending_object, sys_cron_executions, … |
| **Migration discipline** | Indexes must use `CREATE INDEX CONCURRENTLY`, one statement per file; new `CHECK` constraints are added `NOT VALID` then validated; conditionally skipped migrations require idempotent DDL later | The runner executes files outside transactions, which is why the migrations directory holds many single-index files |

## ER diagrams by domain

A single diagram of every table is unreadable, so the schema is split into eight domains. Edge labels name the column that carries the relation. `||..o{` is one-to-many and `}o..o{` is many-to-many; all of it is maintained in application code.

Custom field values are stored as JSONB directly in `issue.properties`, keyed by the property definition's UUID.

`agent_task_queue` is the widest table in the database (70+ columns). It is the queue, the lifecycle record, the session-continuity anchor, and the **attribution audit** at once. `originator_user_id` (the authorization basis, the top-of-chain human in agent-to-agent chains) and `accountable_user_id` (audit and cost attribution) are deliberately separate columns. Five self-referencing columns (parent, escalation, delegated_from, retry_of, rerun_of) preserve the full task lineage.

## Polymorphic relationships

The flip side of having no foreign keys is that polymorphic relations are used freely. "Discriminator column plus ID column" is the most frequent modeling gesture in the schema, and it is how agents appear with equal standing in every collaboration scenario:

| Table · discriminator | May point at | Meaning |
| --- | --- | --- |
| `issue.assignee_type` | `member \| agent` | Core polymorphism: an issue is assigned to a person or an agent |
| `issue.creator_type` / `project.lead_type` | `member \| agent` | Creator / project lead |
| `comment.author_type` | `member \| agent \| system \| plugin` | Four author kinds; edit rights match on the exact (type, id) pair |
| `inbox_item.recipient_type` · `.actor_type` | `member \| agent` (actor also `system`) | Both recipient and actor of a notification may be an agent |
| `issue_subscriber.user_type` / reaction `actor_type` | `member \| agent` | Subscriptions and reactions |
| `attachment.uploader_type` | `member \| agent` | Uploader; the mount point is one of six nullable columns |
| `squad_member.member_type` | `agent \| member` | Mixed human-and-agent squads |
| `autopilot.assignee_type` / `quick_action.assignee_type` | `agent \| squad` | Automation executors are agents or squads, never people |
| `agent_invocation_target.target_type` | `workspace \| member \| team` (reserved) | Subjects of the invocation allowlist |
| `pinned_item.item_type` | `issue \| project \| view` | Personal pins |
| `issue_label.resource_type` | `issue \| agent \| skill` | One label catalog serves three resources, each with its own join table |
| `agent_task_queue.trigger_evidence_kind` | `comment \| issue_assignment \| autopilot_run \| rule_version \| rerun …` | Trigger evidence pointer, free text for extensibility |
| `plugin_storage.scope_type` | `workspace \| user` | Scope of plugin key-value storage |

<Callout type="info">
A cheat sheet for reading any table. Who owns it: `workspace_id` means a tenant asset, `user_id` means a personal asset (PATs, pins, view preferences, Composio connections). Who may change it: look for `owner_id` / `created_by`, the resource owner (see [resource-level permissions](/developers/auth-and-permissions#resource-level-permissions)). Is it a queue: look for `lease_token` / `next_attempt_at`, the outbox pattern.
</Callout>
