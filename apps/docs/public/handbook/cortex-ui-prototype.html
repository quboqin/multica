为什么不给新对象建新的顶层导航

侧栏现有四段结构承载了 12 个条目。文档 / 表格 / 工作流 / 知识库若各自新建一个顶层域，侧栏会变成八个域、用户每次都要先想「这东西住在哪」。 本设计的取舍是：新对象只是既有分组里的新条目，跨对象的入口统一走搜索（⌘K）与「固定」。 「固定」区在现有实现里已支持钉住视图、issue、项目（app-sidebar.tsx 的 pin 逻辑），扩展成可钉文档与表格是零结构改动。

共享视图栏是 FR-002 的验收面

右上角的 DataSource: issue 在原型里是显式可见的，正式版应移除。它在这里的作用是让评审者一眼确认： 切到 S4 的表格页时，视图栏是同一个组件，只有 DataSource 换成了 collection。 如果两处的过滤/分组交互出现任何差异，就说明抽象没做干净。
  • 既有布局 5 种（ViewMode = board | list | table | gantt | swimlane，源自 packages/core/issues/stores/view-store.ts）保持原样
  • 新增 2 种：日历 FR-004、画廊 FR-005，用蓝点标记

列表里多出来的一列：kind 徽章 FR-011

引入 issue.kind 后，同一个列表里会同时出现工作项 / 文档 / 知识候选 / 流程实例。 设计上必须让它们可区分但不喧宾夺主 —— 用 11px 徽章而不是图标或颜色底纹， 并在视图栏第一个过滤 chip 固定为「类型」，默认值 全部。

需要你确认的产品判断：默认值应该是「全部」还是「仅工作项」？ 我倾向 全部（否则文档永远不会被偶遇），但这会改变所有老用户的默认列表内容。

刻意没有出现在这个列表里的东西：record

表格的行（record）不进 issue 列表、不进收件箱、不占用 MAGI- 编号序列 —— 这是 D-1 决策的直接后果，也是 FR-024 的验收标准之一。 建 1000 行 record 后，这一页应当没有任何变化。

S2 · 文档：正文里嵌一个活着的看板

文档是 kind=doc 的 issue FR-011，因此天然带评论、mention、附件、agent 可寻址性与全文检索。 正文编辑器 零改动复用 现有 TipTap 实现 FR-014。 本屏唯一的新组件是正文中央那个 内嵌活视图块 FR-032 —— 它是本产品对 Notion / 飞书的核心差异点。

为什么内嵌块要显式露出 Markdown 串

平台以 Markdown 作为存储与交换格式，编辑器已有 !file[名称](url) 这一自定义语法先例 （packages/views/editor/extensions/file-card.tsx，带双向 roundtrip 测试）。 collection-view 块沿用同一前缀风格 FR-033， 在原型里把序列化结果印在块底部，是为了让评审者确认：这块东西经过 Markdown 往返不会丢， 在 CLI、agent 上下文、纯文本客户端里降级为一个普通链接而不是乱码。正式版这一行应默认隐藏。

「实时」这个词在这里只指数据，不指协同

绿点表示嵌入的是 linked view（视图 ID + 本地覆盖），源表变了这里就变 FR-034。 它不表示多人实时协同编辑 —— 一期明确不做 NG-2 / A-1。 这两件事在界面上极易被用户混淆，所以正文区不使用任何「其他人的光标」类视觉语言， 冲突处理走段落级软锁提示 FR-017 与版本历史 FR-018。

本轮新增：内嵌块的写回必须复用既有的运行确认

改 record 只是改数据；改 issue 会触发平台行为。在这个块里把一张 issue 卡片拖到「进行中」， 可能唤醒一个 agent、关闭一个 stage barrier、往别人收件箱里塞一条。

好消息是平台已经解过一次这道题：表格视图里把 agent 负责的 issue 从 backlog 改成 todo 时， 不直接应用，而是弹一个运行确认框。内嵌块必须复用这个机制，而不是另写一套写回 —— 见 FR-032、验收 AC-14。

另加一条一次性提示：首次在内嵌块里编辑时提示「这条修改会写回源表『需求池』，另有 2 篇文档正在引用它」，之后不再出现。 Notion 老用户知道 database view 是活的，新用户第一反应一定是「我只是在这篇文档里改改」。

右栏第二个 tab 是这次设计里最容易被砍、但最不该砍的东西

「反向引用」把 FR-036 从一个删除确认弹窗提升成常驻面板。 理由：一旦表格可以被 N 篇文档以不同过滤条件嵌入，「这张表还有谁在用」就成了删除、改字段、改选项之前的必查项。 Notion 在这件事上做得很差（引用关系不可见），是可以直接拿来做差异化的点。

本轮修订：status 与 assignee 都不隐藏，「kind-aware」= 换措辞而非藏字段

draft / reviewing / published 分别挂到 todo / in_review / done 三个内置 category FR-016。 代价是文档头部会出现一个状态 chip —— 看起来像「文档为什么有工单状态」。 设计上的处理是：状态 chip 放在标题上方的元信息行，而不是像 issue 那样放在右侧属性面板的第一项， 并且用文档自己的词（草稿 / 评审中 / 已发布），不出现 todo / done 这类工单词汇。

负责人同样不隐藏，但理由完全不同：知识库语料最大的敌人是腐坏——一篇两年没人管的文档被 agent 检索到当成事实用。 文档的 assignee = 这条语料的责任人，没有它，autopilot 无从定期唤醒复核。

一个必须有意选择的后果：draft 挂在 todo category 上，而只有 backlog 不触发 agent。 所以「新建一篇草稿并把负责人设为某个 agent」会立刻拉起一次 run。这确立了「把文档指派给 agent = 让它去写」的语义， 界面上需要在选择 agent 负责人时明说。

S3 · 插入路径：/view 走现有斜杠命令，不新建入口

编辑器已有斜杠命令扩展（packages/views/editor/extensions/slash-command-extension.ts）， 插入活视图只是往这个列表里加一项。左图是命令面板，右图是选中后弹出的数据源选择器 —— 这一步是产品分叉点：默认给「活视图」还是「静态快照」。

「静态快照」被刻意做成禁用态，而不是不出现

用户会找它 —— 从 Notion / 飞书迁移过来的人第一反应就是「我只想贴一份当时的数据」。 如果直接不给，他们会去截图；给了，则每一份快照都会立刻过期，成为文档里的假事实。 设计上的处理是：把选项显示为禁用，并在旁边给出替代路径（活视图 + 本地过滤锁定某个时间字段）。

这是一条需要你拍板的产品取舍，不是纯 UI 问题。我的建议是一期不做快照。

「新建表并嵌入」是这一屏里最重要的一条

它把建表的入口从「先去表格页建好、配好字段、再回文档引用」压缩成一步。 Notion 的核心增长路径正是这条 —— 用户在写东西的过程中顺手建了数据库。 对我们来说它还有额外价值：新表默认落在当前 project 下，避免 workspace 级表格野蛮生长。

「工作项（内置集合）」出现在数据源列表里

这一条不是凑数：它是共享引擎层在用户面前的第一次显形 —— issue 只是一个内置集合，所以它当然也能被嵌进文档 FR-002。 「在周报里嵌一个本周 issue 看板」是这套架构几乎免费得到的能力，而且是日常最高频的用法。

权限在这一步就要处理，不能推到渲染时

选择器只列出当前用户可见的表与视图（含 private 视图仅自己可见）。 但文档会被分享给更多人 —— 所以插入时需要提示：「本文的 3 位协作者中有 1 人无权访问该表，他们看到的将是占位块」。 一期若不做记录级权限 A-2，这个提示只需按表级可见性计算，成本很低，但能避免最尴尬的一类事故。

现有实现里，字段目录是 workspace 全局、活跃定义上限 20（191_issue_properties.up.sql 的注释与 handler 校验）。 用户完全不知道这个上限的存在，直到某天建不出新字段。 新的 collection 字段目录每表独立、建议上限 50 FR-022 —— 把两个配额同时印在菜单里，是让用户一眼理解「表格的字段不会挤占工单的字段」，这正是方案 C 分层的用户可感收益。

两种 relation 在视觉上必须可区分

「关联工作项」指向 issue（record_link.to_type='issue'），用蓝色带 issue 图标的 chip； 「提出客户」指向另一张表，用中性灰 chip FR-028。 理由：指向 issue 的关联会把用户带出数据世界、进入有状态与负责人的工作世界，这是一次上下文切换，值得一个独立的视觉信号。 最后一行故意留了一个失效关联（已删除 删除线）—— 关联边保留但标记失效，不静默消失。

本轮修正：这一列只能放人，不能放 agent

「负责人」是 actor 类型字段，而现状 actorPropertyKinds 只有 member —— actor 字段今天填不了 agent，也填不了小队。 v0.1 的这一屏画错了（有一行放了 agent 头像），已改为成员。

但 member: 这个前缀是刻意留的扩展点，加宽不需要迁移、也不需要新增字段类型。 而 record 没有 assignee 语义（D-1），actor 属性是它唯一能表达「谁负责」的手段。 建议 collection 侧开到 member / agent / squad —— 见 Q-U3，需要你拍板。

「归档字段」不是「删除字段」

沿用平台既有策略（定义只归档、不物理删除，历史值保持可解析）。 菜单里把这一项标红但写明「不删数据」，避免用户为了「彻底删掉」去反复找别的入口。 字段类型变更同理：只允许安全方向转换，不安全的转换要求新建字段 + 迁移。

底部那行 回收站 6（保留 30 天） 是 record 与 issue 的一处关键差异

issue 走的是状态流转（cancelled 仍在系统里）；record 走的是软删除 + 回收站 FR-024。 表格用户的心智模型是 Excel，删行就该进回收站；工单用户的心智模型是工作流，取消不等于删除。 两种模型不能互相污染，所以两者的删除入口、文案、恢复路径必须显式不同。

「运行一次」按钮旁边那行编译说明必须常驻

编译目标：1 父 issue + 5 子 issue + 4 条依赖边 让用户在点下去之前就知道会发生什么。工作流工具最大的信任问题是「我不知道点了会生成什么」， 而我们的实现恰好有一个非常好讲的答案：它只是帮你建了一串 issue，你随时可以手工接管。 这句话本身就是相对 n8n / 飞书审批流的差异化，值得放在界面上，不要藏在文档里。

右下角的运行态泳道直接复用现有 swimlane 组件

FR-054：流程进度不需要新的可视化 —— 泳道天然表达阶段，看板天然表达状态。 「屏障未开」是唯一新增的语义标记，对应 stageBarrierClosed。

本轮新增：模板必须指定 runner，不允许为空

阶段屏障的真实语义比看上去弱：服务端只检测到屏障关闭、唤醒父 issue 的负责人， 它不会把下一阶段的子 issue 从 backlog 提成 todo；而且父负责人是人类时，这条唤醒通知根本不发送。

所以「运行一次」编译出的父 issue 必须挂一个 agent 或小队当推进者。 这不是可选项 —— 缺了它，流程跑完第一阶段就停住，而且极难排查，因为每个子 issue 看上去都正常完成了。 见 FR-052、验收 AC-11。

画布上没有条件分支的连线样式，这是有意的

条件分支与循环是二期 FR-055。如果一期就在画布上画出带条件的边，用户会立刻去用， 然后发现求值不生效。能力没做，界面就不要暗示它存在。 一期的表达力边界是：阶段屏障 + 依赖边 + 自定义状态 —— 足够覆盖绝大多数审批流与评审流。

「从已有 issue 链反向生成」是冷启动的关键入口

没人愿意对着空画布画流程。而工作区里已经跑过的 issue 链就是现成的流程实例， 把它反向抽成模板 FR-053，用户的第一个模板成本接近零。 这条路径也顺带解决了「模板市场」FR-056 在一期缺位的问题。

它低置信度、与既有条目冲突、而且结论一旦入库会污染后续所有 agent 的推理。 它的动作按钮没有「入库」，只有「丢弃」和「升级为 issue 去核实」。 记忆晋升最大的风险不是漏掉知识，而是把没验证的推断固化成事实 —— 界面必须让高风险条目走不通「一键入库」这条路。

排查这种故障非常痛苦，因为每一层看起来都正常：plugin 装好了、后端连通了、agent 也跑了。 所以把它做成一条常驻状态带，而不是留在日志里。见 FR-048、验收 AC-P8。

置信度条是提炼 agent 给的，不是真值

正式版应在旁边给出它的计算口径（来源数量 / 是否被多次独立提及 / 是否与既有条目冲突）， 否则用户会把它当成系统对内容正确性的背书。 这一条在 PRD 里还没有对应需求 —— 建议补一条 FR：候选条目必须携带可解释的来源链，界面上一键可展开。

「语料来源」在侧栏里是一个独立入口

FR-045 让已发布文档与表格快照自动成为语料。用户必须能回答「知识库里到底有什么、从哪来的」， 否则自托管带来的信任优势会被「黑箱」感抵消 —— 这正是 Notion AI 当前最被诟病的一点。

v0.1 → v0.3 增量评审稿 的七条修订

全部来自 2026-09-09 至 09-10 的源码回读，逐条已并入《Cortex 产品需求文档》第 06 章：
  • workflow 模板必须指定 runner（S7）—— 服务端只唤醒不推进，缺了它流程会静默停住
  • 内嵌块写回复用 issue-run-confirm（S2）—— 改 issue 有副作用，平台已有确认机制可复用
  • 内嵌块首次编辑给一次性提示（S2）—— 说清「改的是源表，另有 N 篇文档在引用」
  • actor 字段今天只能填人（S4）—— v0.1 画错了，已修正；是否给 collection 开到 agent / squad 待拍板
  • 知识库设置页显示 daemon 能力覆盖（S8）—— 让一类静默故障可见
  • 语料入库新增 knowledge_ingest 投递层 —— 照搬 webhook 的幂等 + 租约 + 可重放模式
  • 文档的 status 与 assignee 都不隐藏（S2）—— 「kind-aware」从「藏字段」改为「换措辞」
另有一条设计系统缺口仍未补：tint 色阶（见本屏上方）。建议 P1 开工前先补，成本极低。

这份原型没有回答的三个问题

  • 移动端。本原型只做了桌面 Web（含窄屏折叠），移动端的表格与画布如何降级尚未设计。平台有 apps/mobile，一期是否要跟上需要你定。
  • 权限的界面表达。一期不做记录级 / 字段级权限 A-2，因此原型里没有任何权限控件。若定位是可售卖多租户，这一屏要重画。
  • 空状态与首次使用。四个新对象各需要一套空状态和引导，本轮未做 —— 这是决定新功能能否被用起来的关键一环，建议单独排一轮。
