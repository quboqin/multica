Cortex Product Requirements

Cortex 产品需求文档

在 Multica 上把「文档」「多维表格」「知识库」「工作流」四项能力补齐，并让它们与既有的 issue / comment / agent 对象图共用同一套字段系统与视图引擎。本文给出竞品结论、已定决策与取舍、可独立验收的功能需求，以及本轮逐条回读源码后的修订。

PART 01

背景与决策

四项需求里，真实工作量分布与直觉相反：编辑器已经完整，视图系统已经存在，缺的是承载对象与检索层。本章先把「哪些是已有的」与「哪些是真缺口」分开，再列出已经拍板的三项决策。

1.1起点与收敛

原始诉求是「基于 Multica 构建一个轻量级的、可替代 Notion 和飞书的方案」。经过三轮澄清，收敛为在平台上补齐四项能力：Markdown 编辑器与文档管理、多维表格与可视化看板、知识库接入、可编辑的 Workflow。

一次有意义的收敛：IM 消失了第二轮需求清单里不再出现即时通讯。这不是遗漏——飞书、钉钉、企微、Slack、Telegram 集成已经在生产代码里。产品定位因此从「Notion / 飞书替代品」收敛为「agent 原生的知识与工作流平台」，这个定位更清晰，也更好讲。

1.2核对后的真实缺口

需求已有（复用，工作量趋近 0）真实缺口
① 文档 packages/views/editor/ 是完整的 TipTap 实现：Markdown 双向序列化、斜杠命令、表格、Mermaid、数学公式、附件卡片、mention（含拼音匹配）、代码高亮；Web / Desktop / Mobile 三端共用 migration 中没有任何 doc / page / wiki 表，文档只能寄生在 issue.description；无页面树、无文档库；无实时协同（依赖中无 yjs / y-prosemirror / hocuspocus）
② 多维表格 issue_view 已支持 board / list / table / gantt / swimlane 五种布局，分组排序支持 property:<definitionId>；自定义属性 9 类；自定义状态目录；表格单元格就地编辑已实现（含自定义属性编辑器） 字段目录是 workspace 全局且上限 20 个；视图是「issue 全集上的过滤器」；每一行必然是一个 issue（带编号、status、assignee、进 inbox 与搜索）；issue.properties 值袋上限 16KB
③ 知识库 tool.remote-mcp.v1 plugin 通道已具备，含 sha256 校验、签名、trust tier、加密凭据存储 搜索是 Postgres ILIKE + pg_trgm/pg_bigm 子串匹配，无向量、无 embedding、无图谱
④ Workflow issue.stage 阶段屏障、issue_dependency、autopilot（cron / webhook / manual）、squad 路由、skill 无 workflow 定义对象、无可视化编辑器、无模板实例化；且阶段推进需要一个显式的推进者（见 6.2）

1.3已定决策

ID决策承担的取舍
D-1多维表格的行是独立 record（抽 Collection 层），不是 issue表格行没有评论区、没有 agent 可寻址性；需要讨论的行经 relation 桥接到 issue。排期从「补两个布局 2–3 周」升级为「集合层 6–8 周」
D-2OpenViking 作为知识库默认自托管后端需先过 PoC 门禁；开源版官方定位单用户，多租户隔离是硬风险（Q-1）
D-3rollup / formula 推二期，一期只做 relationrecord_link 一期即显式落表，二期计算层不必改表结构

1.4未确认的假设

以下为非阻塞性假设，本文在其上推进；推翻任一项会触发对应范围重排。

ID假设推翻的后果
A-1实时协同编辑不进一期，文档以异步协作 + 段落级软锁为主需引入 WebSocket + CRDT 持久化，会吃掉整个文档模块预算
A-2客群优先「自用 / 小团队（≤50 人）」，一期不做字段级与记录级权限若定位可售卖多租户，权限模型提到 P0，整体 +4~6 周
A-3部署形态自托管优先，云托管为可选若以云托管为主，OpenViking 的自托管优势失效，选型需重评
A-4单集合目标规模 ≤10 万行，workspace 总量 ≤ 千万行超出则需分区与列式存储，属独立课题
A-5OpenViking 按 workspace 起独立实例做租户隔离见 Q-1：资源成本需在 PoC 中实测，不能事后再说
PART 02

目标与非目标

非目标是本章最重要的部分。功能面积上追赶 Notion 与飞书在任何合理预算内都不成立，把不做的事情写死，是让要做的事情能做完的前提。

2.1目标

ID目标判定方式
G-1让「文档」「数据表」成为与 issue 平级的一等公民，三者共用同一套字段系统与视图引擎三类对象在同一套视图组件下渲染，引擎层无任何具体对象类型的分支代码
G-2用户可自定义多维表格，并像引用文档一样在任意位置引用它一篇文档内嵌活视图，行内可编辑，过滤条件可局部覆盖
G-3平台知识可被 agent 语义检索，运行经验能经人工审核晋升为长期知识agent 经 MCP 检索到晋升后的知识，晋升链路端到端可跑通
G-4工作流可视化定义，一次定义可重复实例化拖出一个三节点审批流并运行，生成对应的 staged 子 issue 链
G-5全栈可自托管，数据不出本地断网环境下四项能力（除外部 LLM 调用）全部可用

2.2非目标 —— 本期明确不做

ID非目标理由
NG-1不自建 IM / 即时通讯五套 IM 集成已在生产代码中，重复建设无收益
NG-2不做实时协同编辑（一期）见 A-1；真要做直接上 Yjs，不自研 OT
NG-3不做 rollup / formula（一期）D-3；计算层不是存储层，表结构预留即可
NG-4不自建向量库 / embedding 服务自研短期打不过成熟方案，且不是差异化所在
NG-5不引入 BPMN / 独立工作流执行引擎阶段屏障 + 依赖边 + 自定义状态已能表达绝大多数审批与评审流
NG-6不做无限画布 / 白板与「知识与工作流」定位无关
NG-7不做字段级 / 记录级权限（一期）见 A-2。一期的现实是「能看见就能改」
NG-8不 fork 修改 OpenViking 核心代码AGPLv3；网络旁路调用不传染，fork 修改则必须向网络用户开源
NG-9不重写编辑器TipTap 实现已完整，工作量为 0
NG-10不做移动端完整表格编辑体验（一期）移动端一期只读 + 行详情编辑

2.3产品定位

一句话定位agent 原生的知识与工作流平台 —— 文档、数据、工作项共用一套引擎，agent 是一等参与者而非附加功能，全栈可自托管。

PART 04

竞品结论

结论先行：没有任何一家同时具备「一等公民多维表格 + 文档内嵌活视图 + agent 原生工作流 + 完整自托管」。这个交集就是位置，其余的功能面积不必追。

4.1入选与排除

入选标准：同时满足「面向团队的知识/数据协作」且「与本方案至少两项能力正面重叠」。

竞品入选理由
Notion文档 + database 一体化的定义者，且已内置 AI Agents，与本方案定位正面冲突
飞书（Lark）+ 多维表格 Base用户点名的替代对象；中国团队事实标准；IM + 文档 + Base + 审批流一体
Airtabledatabase 第一的标杆，自动化与 AI agent 能力最成熟
Teable开源、自托管、Postgres 原生的多维表格 —— D-1 最直接的对标
AFFiNE / Docmost开源自托管文档协作，代表「自托管文档」这一侧的最优解
被排除理由
Linear只有 issue，无文档对象、无 database，重叠面仅一项
n8n / Dify纯工作流编排，无数据层与文档层，是 Workflow 模块的参考而非产品级竞品
Obsidian单机本地优先，无多人协作与服务端对象模型
Confluence文档强、数据表弱、无 agent 原生能力，价格与部署形态与目标客群不匹配

4.4做什么 / 不做什么

  1. 01 · 位置差异化在交集，不在面积Notion / 飞书 / Airtable 强在功能面但不可自托管；Teable 可自托管但只有表；AFFiNE 只有文档。四项能力的交集目前无人占据。
  2. 02 · 打法赢在两个结构性优势（a）agent 与人在同一套对象上协作并互相评审；（b）运行经验可晋升为团队长期知识与可复用 skill。这两项在矩阵中本方案独有，且竞品的架构决定了它们补不上。
  3. 03 · 约束自托管是硬约束，不是加分项它直接决定了 D-2：知识库必须能自托管，这是 OpenViking 优于托管商业服务的根本原因。
PART 05

功能需求

优先级定义：P0 一期必须交付，缺失则整体不成立；P1 一期内交付，可延后 2–4 周；P2 二期。带 本轮修订 标记的条目在第 06 章有完整依据。

5.1共享引擎层

依赖方向是硬约束只允许「具体集合实现 → 共享引擎」，引擎层不得反向依赖任何具体对象类型。这条一旦破了，方案 D-1 的全部收益都会随两套视图系统的漂移而消失。
ID优先级需求怎么算做完
FR-001P0字段系统从 issue 专用抽为通用能力：类型定义、校验、选项管理、JSONB 值袋读写在 issue 与 collection 之间共用同一份实现新增一个字段类型时，issue 与 collection 同时获得该能力，无需改两处代码
FR-002P0视图组件引入 DataSource 抽象，table / board / gantt / swimlane 的数据源从 issue store 解耦同一个 table 组件分别挂 issue 源与 collection 源，渲染与交互行为一致
FR-003P0issue_view 增加可空 collection_id；为 NULL 时行为与现状完全一致升级后所有存量视图行为不变；down 迁移可直接 drop 列
FR-004P0新增 calendar 布局：按任一 date 字段排布，支持月/周视图issue 与 collection 均可切到 calendar，拖拽改期回写字段
FR-005P0新增 gallery 布局：卡片网格，可指定封面字段与展示字段同 FR-004 的双源验收
FR-006P1分组能力扩展到 select 之外（date 按周期分桶、checkbox、actor、relation）看板可按负责人、按日期区间分组
FR-004 / FR-005 的双源验收不是加严，是唯一的验证手段如果日历只在 collection 上做出来了，那说明它是新写的组件，没有接在共享引擎上——FR-002 就没真正落地。这两条验收是 R-1（两套视图系统漂移）唯一可执行的防线。

5.2文档

ID优先级需求怎么算做完
FR-011P0引入 issue.kind，取值 task / doc / knowledge / workflow_run，默认 task存量 issue 全部为 task，行为无变化；创建文档得到 kind=doc 的对象
FR-012P0文档层级树：复用 parent_issue_id，支持拖拽调序与跨层移动可建 5 层深的页面树，拖动子页到另一父页后路径与面包屑正确
FR-013P0文档库导航：按 project / workspace 两级作用域展示文档树，支持收藏与最近访问侧栏可展开文档树；收藏与最近访问各自可用
FR-014P0文档正文复用现有 TipTap 编辑器，不做任何重写编辑体验与现有 issue description 一致，含斜杠命令、Mermaid、公式、附件
FR-015P0文档全文检索纳入现有搜索，并可按 kind 过滤搜索结果中文档与 issue 分组展示，可只看文档
FR-016 本轮修订P0文档专属状态集 draft / reviewing / published，分别挂 todo / in_review / done category。status 与 assignee 均不隐藏；priority 默认不显示但保留文档可提交评审、通过后发布；发布态在文档库中有明确标识。见 6.2 修订七
FR-017P1段落级软锁：同一段落被他人编辑中时给出提示，不阻断保存编辑同一段落时后保存者收到冲突提示与差异对比，不静默覆盖
FR-018P1文档版本历史：保存快照，可查看与回滚可查看最近 50 个版本并回滚到任一版本
FR-019P2实时协同编辑（Yjs + y-prosemirror + 服务端持久化）见 NG-2

5.3集合与多维表格

D-1 的边界行是独立 record，不是 issue。代价是表格行没有评论区、没有 agent 可寻址性；需要讨论的行通过 relation 桥接到 issue。这条边界一旦为了方便而破例，方案 C 的分层就会失守。

源码复核与修订

v1.0 的附录曾诚实标注「本轮未能再次拉取源码复核」。这一版补上了：2026-09-09 至 09-10 逐条回读了源码，两个关键数字从转述升级为事实，另有七条结论会改变实现形态。本章是 v1.0 到 v1.1 的全部差异。

6.1升级为事实的结论

结论v1.0 的效力本轮核实结果

6.2七条修订

修订一 · FR-052 增加必填的 runner 字段。屏障关闭时服务端只检测并唤醒父 issue 的负责人，不会把下一阶段从 backlog 提升为 todo；且父负责人是人类时唤醒通知根本不发送。因此「运行一次」编译出的父 issue 必须挂一个 agent 或小队。缺了它，流程跑完第一阶段就停住，而且极难排查——每个子 issue 看上去都正常完成了。

修订二 · FR-032 内嵌块的写回必须复用 issue-run-confirm。改 record 只是改数据；改 issue 会触发平台行为。在文档内嵌块里把一张 issue 卡片拖到「进行中」，可能唤醒一个 agent、关闭一个 stage barrier、往别人收件箱里塞一条。平台已经解过一次这道题：table 视图里把 agent 负责的 issue 从 backlog 改成 todo 时，不直接应用，而是弹确认框。内嵌块必须复用该机制，而不是另写一套写回。

修订三 · FR-032 增加首次编辑的一次性提示。用户第一次在文档里改内嵌表格时，很可能以为只影响这篇文档。提示文案应指明「这条修改会写回源表 X，另有 N 篇文档正在引用它」，之后不再出现。

修订四 · FR-023 需拍板 collection 的 actor 字段是否开放 agent / squad。现状 actorPropertyKinds 只有 member——actor 字段只能填人。但 member: 这个前缀是刻意留的扩展点，加宽不需要迁移也不需要新类型。而 record 没有 assignee 语义（D-1），actor 属性是它唯一能表达「谁负责」的手段；限制成只有人，等于把 agent 排除在自己的数据表之外。建议开到 member / agent / squad，代价是两侧行为分叉，需在 FR-001 中写明该差异是有意的。

修订五 · FR-048 增加 daemon 最低能力要求。remote-mcp-v1 是「remote-MCP 类 plugin 能否投递到某台守护进程」的开关，且判定是失败即关闭。用户机器上的 daemon 版本过旧、不声明该能力时，知识库工具不会被投递，而且是静默的——agent 不报错，只是手里没有那几个工具，照常回答。PoC 验收须明确最低能力要求，并在知识库设置页显示「N 个 runtime 在线，其中 M 个不支持 remote-mcp-v1」。否则排查「为什么 agent 查不到知识库」会非常痛苦，因为每一层看起来都正常。

修订六 · FR-045 增加 knowledge_ingest 投递层。入库是「平台内事件 → 外部系统写入」，幂等问题与 webhook 入站同构：文档反复发布撤回、worker 中途重试，都可能写重。平台已有现成模式可抄——投递层与执行层分离、(doc_id, revision) 唯一索引兜底正确性、租约 worker 负责推送与退避。照搬还白拿了重试可见、失败原因可查与可重放；最后一条在 PoC 阶段反复更换后端与 embedding 配置时会天天用到。

修订七 · FR-016 文档不隐藏 status 与 assignee，「kind-aware」从「藏字段」改为「换措辞」。三个字段的结论：

字段最初的说法现在理由
statusUI 隐藏不隐藏，配 doc 专属状态集published 是语料入库的触发条件，状态就是知识库的准入门槛。藏掉门槛，知识库就成了黑箱
assigneeUI 隐藏不隐藏知识库语料最大的敌人是腐坏。文档的 assignee = 这条语料的责任人；没有它，「这篇过期知识去问谁」没有答案，autopilot 也无从定期唤醒复核
priorityUI 隐藏默认不显示，保留且可在视图中加回文档少有 P0/P1 语义，但「这篇有多重要」可用于检索加权
「kind-aware」的新含义不再是「按 kind 隐藏字段」，而是「按 kind 更换措辞与布局」。同一列，不同说法：文档说「草稿 / 评审中 / 已发布」和「维护者」，工单说「待办 / 进行中 / 完成」和「负责人」。字段一个不藏，用户看到的词全换掉。藏字段会让文档在看板、搜索与批量操作里变成半残的二等公民，换措辞不会。

一个必须有意选择的后果：draft 挂在 todo category 上，而只有 backlog 才不触发 agent。因此「新建一篇草稿并把负责人设为某个 agent」会立刻拉起一次 run。这与 task 行为一致，并确立了「把文档指派给 agent = 让它去写」这一语义。建议保持，并在选择 agent 负责人时明确提示。

6.3概念答疑速查

讨论中反复出现的平台概念，按「最容易被误解的那一点」收敛成一句话。完整推导见架构手册第 09 章。

概念一句话最容易踩的坑
stage vs statusstatus 是纵向的（一个 issue 沿时间前进），stage 是横向的（一组兄弟被切成几批）stage 不是执行闸门，backlog 才是。 stage=4 但状态为 todo 的子 issue 现在就会跑
status 的 categorystatus 是名字，category 是行为等价类——自定义状态声明一个 category 并整套继承其平台行为，没有半继承挂错 category 后果实在：自定义的「等法务确认」挂 in_progress 会被卡死清扫器自动重置回 todo；挂 in_review 才不会被动
actor / multi_actor「人」字段，存 member:<uuid> 前缀引用；multi_actor 是其数组，上限 20、去重保序它和 assignee 长得一样但语义不同：actor 是纯数据，改了不触发任何副作用；assignee 会启动 run、进收件箱、触发小队路由
mention标准 Markdown 链接，协议头 mention://。agent / squad / member / all 有副作用，issue / project 没有@ 一个 agent 是一次真实的计算调度，写在哪都算数。引用他人观点应用纯文本，不用链接形式
mention chip同一个东西的渲染形态：底层永远是那段 Markdown 文本，界面上渲染成胶囊这保证降级安全——在 CLI 与 agent 上下文里退化为普通链接，语义不丢
unfurlMultica 做的是 entity link unfurl：粘贴自家 URL 渲染成 chip；不做 Slack 那种抓 og:image 的网页预览不做通用 unfurl 更像有意取舍：那意味着服务端要代用户访问任意外链，是 SSRF 面也是隐私外泄，与自托管卖点冲突
task claim任务不是推给守护进程的，是抢来的：一条原子 UPDATE + FOR UPDATE SKIP LOCKED，Postgres 本身就是队列按 (issue, agent) 串行——同一 agent 不在同一 issue 上并发，但不同 agent 可以并行
能力协商不是握手，是单向声明 + 服务端裁剪：客户端在 X-Client-Capabilities 里报能力，服务端按对方接得住的形状发响应，失败即关闭为什么不用版本号：没有实现某能力的旧 daemon 会静默跳过字段，在用户要求隔离的工作副本上原地执行
webhook 幂等与租约入站靠 (trigger_id, dedupe_key) 部分唯一索引；下游靠 autopilot_run(webhook_delivery_id) 唯一索引；租约只管调度租约不是 exactly-once 保证。把租约当正确性保证的系统，最终都会在时钟漂移与 GC 停顿上翻车
小队 vs Workflow小队是「人事」（运行时选人，LLM 判断），Workflow 是「流程」（设计时排序，整数确定）两者正交且互相表达不了。小队还有第二个位置容易被漏：作为 workflow 实例父 issue 的推进者（修订一）
一个影响「在产品里写文档」的实现缺陷Mention 的服务端解析是对原始 Markdown 全文跑正则，不排除围栏代码块与行内代码。因此任何一篇解释 mention 语法的文档，只要示例里写了真实 UUID，就会真的把被举例的 agent 拉起来跑一次。本次讨论中已实际触发过一次。影响有界（去重与合并兜底，代价是一次多余的 run），但这个平台的文档、skill 与需求材料都写在产品自身里面，触发条件并不罕见。建议修：匹配前剔除代码段；在修好之前，文档示例一律使用占位符而非真实 UUID。

7.2关键流程

  1. 01 · 插入文档内嵌活视图输入 /view → 选表与已保存视图 → 选嵌入方式（活视图链接；静态快照显示为禁用并给出替代路径）→ 权限提示 → 插入块并序列化为 !view[…](mention://collection-view/<id>) → 可就地叠加本地过滤。
  2. 02 · 渲染块请求 View API携带视图 ID 与本地覆盖；服务端把 JSONB query 编译为 SQL 分页返回；块内行内可编辑，编辑直接写回 record。写回若会触发平台行为，先走确认。
  3. 03 · 晋升知识从运行到长期资产agent run 产生记忆 → autopilot 定时触发提炼 → 生成 kind=knowledge 候选 issue → 置 in_review，人工审核改写（评审动作即评论）→ 置 done 时写回知识库 → 可选提炼为 skill（skill 注册表是唯一事实源）。

Issue（knowledge）candidate → reviewing → promoted / rejectedtodo / in_review / done / cancelled
Record无状态（状态是用户自定义的 select 字段，不是平台语义）——
一个需要在实现时确认的语义知识候选的 rejected 挂在 cancelled 上意味着它是终态，会关闭 stage barrier——即「这条知识被否决」与「已入库」对流程推进是同一个信号。语义上正确，但不该是无意中形成的。

7.4边界情况

情况处理
被引用的 collection / view 被删除内嵌块降级为占位，文档可读；删除前给出反向引用清单
relation 指向的 issue 被删除关联边保留但标记失效，行内显示删除线「已删除」，不静默消失
分组维度上被过滤掉的看板列保留为灰色虚线折叠占位列，不消失（否则用户拖卡片找不到目标列）
collection 超过 10 万行视图强制分页，禁用全表聚合；达到 50 万行触发分区评估
字段类型变更只允许安全方向转换；不安全转换要求新建字段 + 迁移，不做隐式丢数据
字段删除只归档不物理删除，归档字段的值袋数据保留
record 删除软删除进回收站，保留 30 天；表脚常驻回收站条目数
两人同时编辑同一段落后保存者收到冲突提示与差异对比，不静默覆盖；不使用协同光标类视觉
知识库后端不可用knowledge.search 快速失败并降级到平台自带全文搜索；界面上状态带原地变黄写明「已降级」，不弹错误对话框
高风险知识候选低置信度 / 与既有条目冲突时，动作按钮中移除「入库」，只留「丢弃」与「升级为 issue 去核实」
CSV 导入含未知列提示并允许「新建字段」或「跳过该列」，不静默丢弃
