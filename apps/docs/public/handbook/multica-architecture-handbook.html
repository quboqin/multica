产品形态

Multica 把同时运行多个编码 CLI 的工作方式收敛为任务管理平台：智能体是一等公民，可以被指派任务、发表评论、改变状态。平台负责协作与编排，守护进程领取 task 后启动运行时 CLI；本地运行时在用户机器上执行，云运行时在相应执行节点上运行。执行位置不等于模型推理位置，也不保证代码、上下文或工具输出不被发送到平台及外部服务，详见 §05 执行与数据边界。产品支持自部署（Docker Compose），CLI 通过 goreleaser + Homebrew tap 分发。

PART 02

系统架构

五个视角：包拓扑、后端请求管线、实时双 Hub、daemon 任务执行链路、前端状态规则。合在一起就是一条完整的因果链——一次指派如何变成另一台机器上的一次 CLI 执行，再实时流回每个人的屏幕。

2.1Monorepo 拓扑与包边界

前端是 pnpm + Turborepo 管理的 TypeScript monorepo；后端 server/ 是独立 Go module，不在 pnpm workspace 里。共享包发布裸 .ts/.tsx 源码，由消费方（web/desktop）自行编译，依赖方向被硬性约束为 views → core + ui，core 与 ui 互不依赖。

包边界是硬约束（违反即 review 打回）：

包禁止原因

packages/ui@multica/core · 业务逻辑原子组件必须可独立复用
packages/viewsnext/* · react-router-dom · 定义 store同一份页面代码跑在两种路由器上，导航一律走 NavigationAdapter / <AppLink>

从客户端到 server：实际 HTTP 访问路径

图 2-1(a) 回答代码怎样复用；图 2-1(b) 回答请求从哪个进程发出、走到哪个 server 入口。这里把 App 分成 Electron 桌面端和移动端，并把桌面界面、桌面主进程、本机 daemon 分开。下文依据 docs/architecture-handbook@924a6aaf6 的源码，业务基线为 dcc2d5825；不代表所有已部署客户端都已升级到该版本。

桌面界面访问任务、评论等 API，不需要经过本机 daemon。桌面主进程通过本地 IPC 接收登录信息、管理 daemon，并用用户 JWT 调 POST /api/tokens 为 daemon 获取另一枚 PAT（见图 2-2(b)）。CLI 的普通业务命令也直接请求 server；仓库 checkout 等本机功能可另行调用本地 daemon，不能把它们画成全部 CLI 请求的必经层。

调用方HTTP 入口 / 用途凭证从哪里来、放哪里身份与工作区
Web/api/*；默认同源，也可配置独立 API origin登录设置 multica_auth HttpOnly Cookie（内含 JWT）；前端读 multica_csrf，写请求加 X-CSRF-Token登录用户；一般以 X-Workspace-Slug 选择工作区，再验成员资格
桌面界面配置的 API 地址下 /api/*登录 JWT 存于 renderer 的 localStorage["multica_token"]；HTTP 显式带 Bearer登录用户；X-Workspace-Slug + 成员校验
移动 App配置的 API 地址下 /api/*登录 JWT 存于 SecureStore；独立 API client 显式带 Bearer登录用户；X-Workspace-Slug + 成员校验
人工 CLI/api/*；查询、评论、更新任务等浏览器登录换取 mul_ PAT，保存到选定 profile；也支持导入 token；请求带 BearerPAT 所属用户；通常用 X-Workspace-ID 选择工作区
daemon/api/daemon/register、task 进度与结果接口；heartbeat / tasks/claim 是 WS 优先路径的 HTTP 回退本机通常读 profile 中的 mul_；桌面管理的 daemon 使用主进程换取的 PAT；云节点可用 mcn_PAT/JWT/mcn_ 路径得到用户身份，再由 handler 检查工作区及端点要求；mdt_ 路径用绑定的 workspace/daemon 上下文
任务内 CLI仍是业务 /api/*，例如发布评论server 领取时签发 mat_，daemon 注入 MULTICA_TOKEN；任务上下文禁止回退到全局用户 token署名为 agent；server 绑定 task/agent/workspace/runtime 属主，工作区不可由客户端换走

Bearer 是 HTTP 的携带方式，JWT、PAT、mat_ 是凭证种类；两者不是同一级概念。Web 的 Cookie 中也装着 JWT。Bearer 分支不做 Cookie-CSRF 校验，但仍要验证凭证和权限。旧版 Web 的 localStorage token 兼容路径可使用 Bearer；上表描述正常的新登录路径。独立 API origin 还需满足 CORS、Cookie 域及 SameSite 条件；跨 origin 不一定跨 site，不能只改 API 地址就假设 Cookie 一定能携带。

2.2后端分层与请求管线

后端是单体服务，但分层非常规整：chi 路由集中在 server/cmd/server/router.go（约 2400 行，路由即文档），HTTP 业务路由通常走 handler → service → sqlc 生成代码；实时入口另有 Hub 处理链。入口与认证方式如下图分开列出。写操作在 handler/service 里同步发布进程内事件（events.Bus），实时推送由此派生（见 §2.3）。

server 入口接受什么关键边界
业务 /api/*Bearer：JWT、mul_、mat_、mcn_；正常 Cookie 会话使用 JWTAuthorization 优先；Cookie 写请求缺失/错误 CSRF 返回 403。认证成功不等于有工作区或资源权限
/api/daemon/*Bearer：mdt_、mcn_、mul_、JWT只看 Authorization；不接受 Cookie，也不接受 mat_。mdt_ 是支持的机器凭证分支，不能据此推断所有 daemon 默认都用它
/wsCookie，或升级后的首帧 JWT/mul_不走业务 Auth；不读取 HTTP Bearer 作这一入口的 token 认证，不把 token 放 URL；mat_/mdt_/mcn_ 不适用
/v1/*Bearer：mpi_ 安装令牌 / mpc_ 调用令牌用户 JWT/PAT/Cookie 不能代替插件凭证。面板通过宿主 MessagePort → /api/plugin-bridge/v1 使用用户会话
其他直接入口登录验证码/OAuth；webhook 提供方签名或端点令牌；下载/头像/面板的签名能力 URL“不走 Auth”不等于“无需验证”。不同 webhook 的验证方式不同，不能画成统一的用户会话入口

X-Workspace-ID / X-Workspace-Slug 是资源选择信息，不是认证凭证。mat_ 验证后由 server 覆写身份头并固定工作区；mcn_ 交给 Cloud 验证并关联本地用户，未配置验证器则拒绝，Cloud 不可达返回 503。不能把发起人的名称、客户端类型或自行填写的身份头当作权限来源。

登录之后：用户会话怎样变成 CLI / daemon 凭证

用户 JWT 默认 30 天，可由 AUTH_TOKEN_TTL 配置；移动端直接保管登录返回的 JWT，不创建本机 daemon PAT。凭证过期或被撤销需重登/重铸，网络错误与 5xx 不应被解释成“凭证已失效”。本节只描述已有实现，不引入新的认证协议。

2.4Daemon 与任务执行链路

以本地运行时为例：平台负责编排，执行发生在用户自己的机器上。daemon 内嵌在 multica CLI 里（multica daemon start），机器级批量轮询器先占本机执行槽，再跨该机所有 runtime 批量领取任务。

准入判定不是简单的入队：internal/dispatch 定义了一套 ReasonCode，把「为什么没跑」变成可观测的一等结果——

queued coalesced 合并进行中任务 deferred 延后 invocation_not_allowed 无调用权限 runtime_offline attribution_blocked 无可归责人 already_active self_trigger_suppressed 防自触发

Runtime 分三层：① pkg/agent.SupportedTypes 白名单定义 24 个协议族（claude、codex、cursor、copilot、kimi、opencode、qwen、grok……），每族一个后端文件负责启动参数与流式输出解析；② 内建 runtime 目前只有 omp（Oh-My-Pi，讲 pi JSON 协议）；③ 工作区可定义自定义 runtime profile（command_name + fixed_args），但 protocol_family 必须落在白名单内（DB CHECK + 应用双重校验）。

2.5前端架构与状态规则

前端最重要的架构决定是服务端状态与客户端状态的硬分界，写进 CLAUDE.md 成为 review 准绳：

归属管什么规则
TanStack Query一切来自 API 的数据：issues、members、agents、inbox、workspaces…工作区级查询 key 必须包含 wsId；如 ["issues", wsId, "list", sort]。WS 的服务端数据更新进入 Query 缓存
Zustand筛选器、草稿、弹窗、标签页布局、导航历史共享 store 只能放在 packages/core；禁止把服务端载荷镜像进来；selector 必须返回稳定引用

一次典型读写的完整路径：

  1. 读：视图用 issueKeys.listSorted(wsId, sort) 建 key → api.listIssues() 自动盖上 Authorization / X-Workspace-Slug / X-CSRF-Token 头 → 响应过 parseWithFallback + zod schema——契约漂移时降级为空兜底 + 告警日志，而不是白屏。这是「已安装桌面端要能对上新版后端」的核心防线。
  2. 写：useUpdateIssue 的 onMutate 同步补丁所有可确定缓存并快照；服务端 loadIssueForUser 解析路径参数、支持 expected_revision 乐观并发；成功后发布 issue:updated（带变更标记位）。
  3. 回声：WS 帧到达 useRealtimeSync → ws-updaters 补丁确定投影、失效不确定投影；mutation 的 onSettled 再失效一轮；onError 用快照回滚。断线重连或切工作区时全量失效工作区级查询。
乐观更新的四个前置条件结果可本地预测、用户停留原屏、失败罕见、回滚廉价——四者齐备才允许乐观（典型：状态/指派/开关补丁）。会导航或需确认的流程（创建/删除/退出）必须等服务端返回；聊天发送用「可见 pending + 失败重试」模式，不做无痕乐观。

平台适配的缝只有几条，全部显式：NavigationAdapter（web 包 next/navigation，desktop 写 tab store）、StorageAdapter（web/desktop 用 localStorage，mobile 用 Keychain）、CoreProvider（唯一构造 ApiClient/auth store/i18n/WSProvider 的地方）、setCurrentWorkspace（路由驱动的工作区镜像，用于请求头、持久化命名空间与重连）。桌面端是「单路由多标签」体系：标签是可序列化的 TabSession，tab-coordinator 是唯一写路由器的地方；工作区前的一次性流程（建工作区、接受邀请）不是路由，是 WindowOverlay 状态。

PART 04

认证与权限

一句话概括：无密码的人类认证（JWT + Cookie），前缀分流的七类凭证，以「工作区成员」为地基、角色与资源属主逐层收窄的授权体系——而 agent 从头到尾没有自己的账号，它的身份是一枚随任务生灭的令牌。

4.1无密码登录

整个系统没有密码：user 表没有密码列，也就不存在密码哈希与找回流程。登录只有两条路，全部在公开路由组；对应的按 IP 限流需配置请求路径 Redis（见 §8.1）：

会话是无状态 JWT：HS256 签名（JWT_SECRET，生产环境弱密钥直接拒绝启动），claims 只有 sub/email/name/exp/iat，没有 sessions 表，因此没有「注销其他设备」，也没有刷新流程——过期即重新登录。POST /auth/logout 只清 Cookie，被复制走的 JWT 在到期前仍然有效；可吊销的凭证只有 PAT / daemon / task / plugin 令牌。

4.2凭证家族

凭证前缀用于区分类别和选择验证器，不能仅凭前缀推断可访问的接口。编码和存储因凭证而异：插件令牌使用 URL-safe Base64；mpc_ 的哈希及 grant 保存在进程内存，mcn_ 由 Cloud 验证。各端携带方式及入口差异见 图 2-1(b) 与 图 2-2。

4.3请求鉴权管线

主认证中间件 middleware.Auth 做的第一件事是 r.Header.Del("X-Actor-Source")——这个头只能由服务端盖章，客户端传入一律丢弃。随后取凭证（Authorization 头优先于 Cookie；Cookie 承载的写请求必须过 CSRF），按前缀分流：

前缀查验盖章到请求头
mat_task_token 按哈希查、未过期X-User-ID（属主）· X-Agent-ID · X-Task-ID · X-Workspace-ID 全部覆写客户端值，再盖 X-Actor-Source: task_token
mcn_HTTP 调 Cloud /pat/verify；本地必须有对应 user 行X-User-ID + X-Actor-Source: cloud_pat
mul_Redis 缓存 → personal_access_token（未撤销、未过期）X-User-ID

身份在进程内的传递方式很朴素：handler 用 r.Header.Get("X-User-ID") 取用户；工作区成员行则放进 context（MemberFromContext）。鉴权缓存全在 Redis：PAT 10 分钟、成员资格 5 分钟、daemon 令牌与 Cloud PAT 各有缓存——官方声明的最坏撤销滞后为 10 分钟。

4.4工作区作用域与角色

4.6Daemon 与 Agent 身份

/api/daemon/* 使用独立的 DaemonAuth：只收 Authorization 头（结构性排除 Cookie/CSRF 问题），支持 mdt_ / mcn_ / mul_ / JWT 四条路径。实践中 daemon 主要以属主的 mul_ PAT 运行；runtime 访问经 requireDaemonRuntimeAccess 校验，且刻意用「404 = runtime 已不存在，daemon 应丢弃并重注册」作自愈信号（其余 DB 错误保持 500，防止抖动触发自清理）。

Agent 没有账号，身份是随任务生灭的 mat_ 令牌——这是全系统最精彩的安全设计：

  1. 铸造：daemon 领取任务时，服务端为每个任务铸 mat_ 令牌，绑定 task + agent + workspace + runtime 属主，24 小时过期，与领取回执同事务落库。runtime 属主缺失时取消任务而不是派发——绝不产生无主凭证。历史上曾把属主的 PAT 注入 agent 进程，此设计（MUL-2600）正是为替换它。
  2. 注入：daemon 把令牌以 MULTICA_TOKEN 环境变量交给 CLI 进程（另有 MULTICA_WORKSPACE_ID / MULTICA_AGENT_ID / MULTICA_TASK_ID 等）；daemon 侧校验注入值必须是 mat_ 前缀，CLI 侧在任务上下文里拒绝回退到用户全局配置的 token，也拒绝 login 等人类命令。
  3. 行权：请求进来后中间件覆写四个身份头并盖 X-Actor-Source: task_token；工作区解析无条件采用令牌绑定值；成员校验跑的是属主的资格——属主成员资格只是其中一层约束；还要满足令牌有效性、绑定工作区、资源权限与端点对 agent 的限制。
  4. 署名：resolveActor 据此返回 ("agent", agent_id)，评论落库为 author_type='agent'。旧路径若想声明 agent 身份，必须同时给出 X-Agent-ID 与归属该 agent 的有效 X-Task-ID——单凭 X-Agent-ID 永远不被信任，成员无法冒充 agent。

4.8攻击面加固

  • CSRF 三层：SameSite=Strict 为主防线；双提交 Cookie 的值是 nonce.HMAC(nonce, 会话JWT)——把 CSRF 令牌与会话绑定，子域写 Cookie 也伪造不了；Bearer 路径与插件 API 结构性免疫。
  • 限流（启用对应 Redis 后，固定窗口 + Lua 原子）：send-code 5/分/IP、verify 20/分/IP、contact-sales 5/时、插件 API 120/分；邀请另有三重滑窗（发起人 10/10min · 工作区 50/24h · 收件人 6/24h，fail-closed）。不同入口的降级策略需分别核对：未配置请求路径 Redis 时认证限流会被禁用，见 §8.1；X-Forwarded-For 仅在可信代理 CIDR 内采信。
  • 能力 URL 替代 Cookie：SameSite=Strict 会挡住 <img>/下载场景，于是附件下载、头像、插件面板都改用短时效 HMAC 签名 URL——凭证在链接里而不在会话里。
  • 启动守卫：生产环境下弱 JWT_SECRET 直接 os.Exit(1)；开发验证码后门在生产硬关闭；保留 slug 表解析失败则拒绝启动（92 个保留字防路由劫持）。
  • 删掉的攻击面：早期的 OpenAI 兼容透传端点 /api/llm/* 已整体移除——它曾允许任何登录用户白嫖部署方的模型密钥。
  • WS 来源校验：同源放行、X-Forwarded-Host 仅信任可信代理、其余按显式 origin 白名单。
值得留意的一处边角middleware.Auth 删除并重盖 X-Actor-Source，但不删客户端传入的 X-User-ID（认证路由会覆写，安全）；唯独公开路由 GET /api/github/setup 直接读取该头写入 GitHub 安装的 connected_by_id。它只用于「谁连接了」的展示归属、不参与任何授权判定，但属于可伪造的归属信息，重构时值得顺手收紧。
PART 05

执行与数据边界

任务级 API 身份、工作目录隔离、操作系统权限和模型的数据流是四个不同的边界。判断一次执行能做什么，需要逐层看，不能只看令牌或目录名称。

5.1API 身份与机器权限

层次当前实现保证的范围
Multica API 身份mat_ 绑定智能体、task、工作区和运行时属主；服务端执行成员资格与资源权限检查限制通过 Multica API 访问的身份与工作区。它不是只允许操作某一条任务的通用 ACL，也不限制操作系统文件访问
执行目录守护进程管理环境目录；本地目录还可选择 in_place 或 worktree减少并发覆盖、隔离配置与保留成果；目录约定本身不阻止进程读取目录外文件
操作系统用户智能体 CLI 作为守护进程的子进程运行，使用该用户可访问的文件、网络与宿主 CLI 凭据必须由实际运行环境确定权限上限。任务级 CODEX_HOME 不等于新的操作系统用户
工具沙箱与审批Claude Code 启动参数包含 --permission-mode bypassPermissions；Codex 按平台和检测到的配置选择沙箱策略不能把无人值守执行描述成统一的强沙箱。应核对启动日志及实际生成的配置

本基线中，Codex 在 Linux 使用 danger-full-access；Windows 未显式配置原生沙箱时也采用该模式，显式 opt-in 路径另行处理；macOS 由版本检测决定是否能保留带网络的 workspace-write，否则回退。实际策略以 execenv/codex_sandbox.go 和该次执行日志为准。

部署边界若需要限制智能体可触达的文件和凭据，应在守护进程之外设置专用操作系统用户、容器或虚拟机，并按任务需要分配目录和凭据。工作区权限与工作目录隔离不能代替这一层。

5.2三条数据路径

本地执行不等于本地推理，也不等于代码永不离开机器。代码是否发送给模型、MCP 或其他服务，取决于运行时、工具配置和实际调用；进入 task_message、结果或附件的内容还会进入平台存储。API 中的密钥脱敏只覆盖对应的字段与出口，不能推导为任意工具输出都会自动脱敏。

自托管决定 Multica API、数据库与对象存储由谁管理；它不会自动把第三方模型或工具变为本地服务。runtime_mode=cloud 则改变执行机器的位置。服务端另有可选的 LLM 辅助层，例如生成聊天标题，应与守护进程启动的编码 CLI 分开理解。

5.3用一组标识串起审计

排查一次执行时，记录 workspace_id、issue_id（若有）、task_id、agent_id、runtime_id 与 daemon_id。调用授权看链顶人类 originator_user_id，成本和审计归责看 accountable_user_id，API 认证还涉及任务令牌绑定的运行时属主；这几个身份可能不同。

任务令牌有 24 小时有效期，终态路径还会尝试删除该 task 的令牌。过期校验与删除是两道不同机制；删除失败应查服务端日志，不能仅凭界面已完成就证明凭据已清理。

PART 06

状态机与异常恢复

正常执行只是主路径。分布式系统还要回答：请求是否送达、数据库是否提交、本机进程是否仍在运行，以及用户是否已经看到结果。

PART 07

执行目录与成果生命周期

平台保存了执行记录，不代表已经保存了所有本地文件。理解工作目录的来源、复用与清理，才能找到成果，并解释并发执行是否会影响用户的 checkout。

7.1三种目录安排

模式目录与并发成果位置
守护进程管理的工作区在配置的 WorkspacesRoot 下解析稳定环境根，准备仓库与上下文；环境根有独占声明，避免执行与清理互相覆盖环境中的工作目录、结果分支和会话文件；具体仓库准备方式由执行路径与 provider 决定
本地目录 in_place在用户指定目录直接执行；模式字段为空时仍按此处理。同一规范化路径上的执行通过路径锁串行直接改动原目录。执行前后的文件差异需要在原 checkout 检查，不能假设任务结束就能还原
本地目录 worktree在环境根内创建用户仓库的独立 worktree；绕过整段执行的路径串行锁，Git 管理操作仍受仓库级锁保护通常交付用户仓库内的 agent/<name>/<short-task-id> 分支；收尾失败时保留 worktree 路径供恢复

这里描述的是守护进程如何安排正常执行。worktree 减少文件写入冲突，但其目录位置不会限制拥有宿主用户权限的进程访问其他目录；权限范围仍见 §05。

7.2从用户目录到可恢复的结果

未跟踪文件复制受数量和大小限制：本基线为 2000 个、200 MiB，并遵循 Git 的忽略规则。无法完整复现纳入复制范围的文件时，准备阶段报错退出；不是静默以缺失文件的环境继续运行。存在用户未提交内容时，还会在执行分支记录基线提交，以区分原有内容与智能体新增结果。

收尾阶段可能自动提交智能体遗留的未提交修改；如果没有新增成果，则清理空结果分支。提交失败或收尾被判定不安全时，返回 PreservedPath 并保留 worktree。这里的结果分支是本地成果指针，不代表已推送、已合并或已通过测试。

锁文件与活动锁仓库级 multica-worktree.lock 位于 common Git directory，由进程持有文件锁。同一仓库的多个 linked worktree 共享这道协调。文件存在不等于锁仍被占用；不要通过删除锁文件解除竞争，否则可能让两个进程分别锁住不同 inode。

7.3会话复用、清理与找回成果

后续执行可以复用先前的目录和 CLI 会话，但服务端的 session_id 只是指针。目录、会话文件或运行时条件不再满足时，需要走新环境或会话恢复路径；不能仅凭数据库中的会话 ID 保证可以续跑。

内容保留与回收边界检查方式
执行记录与结果摘要在服务端数据库；不等于完整 Git 仓库、构建输出或 CLI 会话备份查 task 详情、结果里的 work_dir / branch_name / session_id 与本机日志
用户原目录in_place 不按可丢弃 workdir 清理；托管 sidecar 的清理与用户代码清理是两回事在原仓库查看 git status 与差异
管理的执行环境与缓存守护进程按父任务生命周期、完成时间、孤儿状态、缓存类型等分别执行 GC；活动环境有锁保护查看当前 profile 的 GC 配置与日志。自托管的完成环境独立 TTL 默认关闭，但其他清理规则仍可能生效
收尾失败保留的 worktree保留用于恢复，不是永久归档承诺。应先把有效成果保存到稳定分支或其他持久位置，再处理清理git worktree list、日志中的保留路径、该目录下的 git status

PART 08

部署、存储与故障排查

先确认流量到达哪个服务，再确认数据库与执行机器是否就绪。以下为部署和排查方法，实际可用性需在目标环境逐项验证。

8.1部署拓扑与可选依赖

默认自托管 Compose 启动 PostgreSQL、backend 与 frontend 三个服务；守护进程和已登录的智能体 CLI 运行在执行机器上。Web 和 API 默认分别绑定宿主机 127.0.0.1:3000 / 8080，跨机器访问由 HTTPS 反向代理承接。

路径 / 依赖应到达的位置常见误判
页面与普通 API页面到 frontend；普通 API 可经 frontend rewrite 或按部署方案直接到 backend浏览器能打开首页，不代表执行机器访问的 API 地址也正确
/ws浏览器实时连接到 backend 的 realtime.Hub，代理需转发 WS Upgrade普通 HTTP 代理成功不能证明 WS 升级成功
/api/daemon/ws执行机器到 backend 的机器连接；与浏览器的 /ws 不同漏配后可能回退轮询，表现为能执行但实时唤醒异常
Redis单节点可使用内存 Hub；跨节点实时扇出需显式配置 relay。请求路径缓存/限流与 relay 还可使用不同 Redis 配置默认 Compose 没有 Redis 服务，也未传入 REDIS_URL；仅在宿主 .env 写它不会自动接入容器
邮件与对象存储邮件用于验证码；附件可使用本地上传卷或配置好的 S3 后端API 就绪不表示邮件可投递、附件可下载、智能体已登录
Redis 的关闭语义未配置请求路径 Redis 时，服务端会记录 auth rate limiting disabled: REDIS_URL not configured。因此 §4.8 中的认证限流数值属于启用对应 Redis 限流后的行为，不是所有自托管安装都会自动具备的保证。多副本部署还需同时检查 relay、后台租约及共享附件存储。

要接入 Redis，应在自己的 Compose override 中显式增加服务或外部连接及 backend 环境变量，再核对启动日志。仅配置 REALTIME_RELAY_REDIS_URL 可以让 relay 使用独立实例，但不能据此推断请求路径限流也已开启。

公开 URL 的职责也应分开：MULTICA_APP_URL 指向页面，MULTICA_PUBLIC_URL 提供公开 API 地址；守护进程需要不同地址时使用 MULTICA_DAEMON_SERVER_URL。从实际 /api/config 响应核对 daemon_server_url，尤其留意远程安装是否仍返回 localhost。
