Multica 架构手册

Multica 是一个开源团队工作区——「智能体，也在看板上」。人类与 AI 编码智能体在同一块看板协作：任务派给 agent，它在你自己的机器上接活、边做边汇报、做完交回审核。本手册从源码出发，拆解它的系统架构、数据模型与认证权限体系。

产品形态

Multica 把「同时开着五个终端标签页跑 Claude Code / Codex / Cursor」的散装工作方式，收敛为一个任务管理平台：agent 是一等公民——它可以被指派 issue、发表评论、改变状态，和人类成员一样出现在看板与成员列表里。关键设计是执行与平台分离：平台（server + web/desktop/mobile）负责协作与编排，真正的代码执行由用户机器上的 multica daemon 领取任务后调起本地 agent CLI 完成，代码不出门。产品支持自部署（Docker Compose），CLI 通过 goreleaser + Homebrew tap 分发。

PART 02

系统架构

五个视角：包拓扑、后端请求管线、实时双 Hub、daemon 任务执行链路、前端状态规则。合在一起就是一条完整的因果链——一次指派如何变成另一台机器上的一次 CLI 执行，再实时流回每个人的屏幕。

2.1Monorepo 拓扑与包边界

前端是 pnpm + Turborepo 管理的 TypeScript monorepo；后端 server/ 是独立 Go module，不在 pnpm workspace 里。共享包发布裸 .ts/.tsx 源码，由消费方（web/desktop）自行编译，依赖方向被硬性约束为 views → core + ui，core 与 ui 互不依赖。

包边界是硬约束（违反即 review 打回）：

包禁止原因
packages/corereact-dom · localStorage · process.env · UI 库纯无头层，平台差异走 StorageAdapter 等适配器注入
packages/ui@multica/core · 业务逻辑原子组件必须可独立复用
packages/viewsnext/* · react-router-dom · 定义 store同一份页面代码跑在两种路由器上，导航一律走 NavigationAdapter / <AppLink>
平台 API只能出现在 apps/web/platform/ 与 apps/desktop/…/platform/把 Next.js / react-router 的知识锁进两个目录

2.2后端分层与请求管线

后端是单体服务，但分层非常规整：chi 路由集中在 server/cmd/server/router.go（约 2400 行，路由即文档），进入四类路由组之一后走 handler → service → sqlc 生成代码。写操作在 handler/service 里同步发布进程内事件（events.Bus），实时推送由此派生（见 §2.3）。

值得记住的三个后端事实：

  • 路由住在 cmd/server，不在 internal/handler。handler 是无路由知识的方法集合，router.go 用中间件组合出权限层级，读一个文件即可判断任意端点的鉴权要求。
  • sqlc 是唯一的 SQL 通道：56 个 .sql 查询文件生成 61 个 Go 文件；schema 来源就是 migrations/ 目录本身。
  • 定时任务进数据库：internal/scheduler 用 sys_cron_executions 表做租约 + 审计的 DB cron（用量小时汇总、autopilot 定时调度、插件 hook 调度），多副本部署下不重复执行。

2.3实时体系：双 Hub + Redis 中继

实时层有两个互不混用的 WebSocket Hub：面向人的 internal/realtime（浏览器/桌面/移动端，房间制）和面向机器的 internal/daemonws（daemon 唤醒与 RPC）。所有事件都从进程内 events.Bus 派生——先跑类型监听器（通知、活动、订阅者、插件桥），再由全局监听器序列化成 WS 帧扇出。

协作comment · reaction · subscriber · activity · pin · project(+resource) · label · property
组织workspace · member · invitation · inbox:*（7 种，走 user 房间）

2.4Daemon 与任务执行链路

这是 Multica 最有辨识度的一条链路：平台负责编排，执行发生在用户自己的机器上。daemon 内嵌在 multica CLI 里（multica daemon start），机器级批量轮询器先占本机执行槽，再跨该机所有 runtime 批量领取任务。

准入判定不是简单的入队：internal/dispatch 定义了一套 ReasonCode，把「为什么没跑」变成可观测的一等结果——

queued coalesced 合并进行中任务 deferred 延后 invocation_not_allowed 无调用权限 runtime_offline attribution_blocked 无可归责人 already_active self_trigger_suppressed 防自触发

Runtime 分三层：① pkg/agent.SupportedTypes 白名单定义 24 个协议族（claude、codex、cursor、copilot、kimi、opencode、qwen、grok……），每族一个后端文件负责启动参数与流式输出解析；② 内建 runtime 目前只有 omp（Oh-My-Pi，讲 pi JSON 协议）；③ 工作区可定义自定义 runtime profile（command_name + fixed_args），但 protocol_family 必须落在白名单内（DB CHECK + 应用双重校验）。

2.5前端架构与状态规则

前端最重要的架构决定是服务端状态与客户端状态的硬分界，写进 CLAUDE.md 成为 review 准绳：

归属管什么规则
TanStack Query一切来自 API 的数据：issues、members、agents、inbox、workspaces…工作区级查询 key 必须以 wsId 开头；WS 事件只允许打补丁/失效 Query 缓存
Zustand筛选器、草稿、弹窗、标签页布局、导航历史共享 store 只能放在 packages/core；禁止把服务端载荷镜像进来；selector 必须返回稳定引用
React Context仅平台管道（导航适配、i18n 适配）不承载业务状态

一次典型读写的完整路径：

  1. 读：视图用 issueKeys.listSorted(wsId, sort) 建 key → api.listIssues() 自动盖上 Authorization / X-Workspace-Slug / X-CSRF-Token 头 → 响应过 parseWithFallback + zod schema——契约漂移时降级为空兜底 + 告警日志，而不是白屏。这是「已安装桌面端要能对上新版后端」的核心防线。
  2. 写：useUpdateIssue 的 onMutate 同步补丁所有可确定缓存并快照；服务端 loadIssueForUser 解析路径参数、支持 expected_revision 乐观并发；成功后发布 issue:updated（带变更标记位）。
  3. 回声：WS 帧到达 useRealtimeSync → ws-updaters 补丁确定投影、失效不确定投影；mutation 的 onSettled 再失效一轮；onError 用快照回滚。断线重连或切工作区时全量失效工作区级查询。
乐观更新的四个前置条件结果可本地预测、用户停留原屏、失败罕见、回滚廉价——四者齐备才允许乐观（典型：状态/指派/开关补丁）。会导航或需确认的流程（创建/删除/退出）必须等服务端返回；聊天发送用「可见 pending + 失败重试」模式，不做无痕乐观。

平台适配的缝只有几条，全部显式：NavigationAdapter（web 包 next/navigation，desktop 写 tab store）、StorageAdapter（web/desktop 用 localStorage，mobile 用 Keychain）、CoreProvider（唯一构造 ApiClient/auth store/i18n/WSProvider 的地方）、setCurrentWorkspace（路由驱动的工作区镜像，用于请求头、持久化命名空间与重连）。桌面端是「单路由多标签」体系：标签是可序列化的 TabSession，tab-coordinator 是唯一写路由器的地方；工作区前的一次性流程（建工作区、接受邀请）不是路由，是 WindowOverlay 状态。

PART 03

数据模型

PostgreSQL 17，sqlc 建模 106 张表（合计约 111 张活跃表 + schema_migrations）。最重要的一条设计决定：整库没有一个外键——关系、校验、级联清理全部由应用层显式完成。下面的 ER 图里所有连线都是虚线，提醒你它们是「应用层约定」而非数据库约束。

PART 04

认证与权限

一句话概括：无密码的人类认证（JWT + Cookie），前缀分流的七类凭证，以「工作区成员」为地基、角色与资源属主逐层收窄的授权体系——而 agent 从头到尾没有自己的账号，它的身份是一枚随任务生灭的令牌。

4.1无密码登录

整个系统没有密码：user 表没有密码列，也就不存在密码哈希与找回流程。登录只有两条路，全部在公开路由组、按 IP 限流：

会话是无状态 JWT：HS256 签名（JWT_SECRET，生产环境弱密钥直接拒绝启动），claims 只有 sub/email/name/exp/iat，没有 sessions 表，因此没有「注销其他设备」，也没有刷新流程——过期即重新登录。POST /auth/logout 只清 Cookie，被复制走的 JWT 在到期前仍然有效；可吊销的凭证只有 PAT / daemon / task / plugin 令牌。

4.2凭证家族

所有非 JWT 凭证统一形态：前缀 + 40 位 hex（20 随机字节），服务端只存 SHA-256 哈希。前缀既是路由（中间件按它分流），也是标签（一眼看出凭证类别）：

4.3请求鉴权管线

主认证中间件 middleware.Auth 做的第一件事是 r.Header.Del("X-Actor-Source")——这个头只能由服务端盖章，客户端传入一律丢弃。随后取凭证（Authorization 头优先于 Cookie；Cookie 承载的写请求必须过 CSRF），按前缀分流：

前缀查验盖章到请求头
mat_task_token 按哈希查、未过期X-User-ID（属主）· X-Agent-ID · X-Task-ID · X-Workspace-ID 全部覆写客户端值，再盖 X-Actor-Source: task_token
mcn_HTTP 调 Cloud /pat/verify；本地必须有对应 user 行X-User-ID + X-Actor-Source: cloud_pat
mul_Redis 缓存 → personal_access_token（未撤销、未过期）X-User-ID
其他按 JWT 解析（签名算法钉死 HMAC，拒绝 alg 混淆）X-User-ID = sub，X-User-Email

身份在进程内的传递方式很朴素：handler 用 r.Header.Get("X-User-ID") 取用户；工作区成员行则放进 context（MemberFromContext）。鉴权缓存全在 Redis：PAT 10 分钟、成员资格 5 分钟、daemon 令牌与 Cloud PAT 各有缓存——官方声明的最坏撤销滞后为 10 分钟。

4.4工作区作用域与角色

工作区是权限地基。解析优先级：mat_ 令牌绑定的工作区（无条件优先，其余标识一律忽略）→ URL 参数 → ?workspace_slug / X-Workspace-Slug（web/desktop/mobile 走这条）→ ?workspace_id / X-Workspace-ID（CLI/daemon 走这条）。成员校验失败返回的是 404 而非 403——非成员连「这个工作区存在」都探测不到；前端同样用一张 NoAccessPage 刻意不区分两者。

入口除邀请外还有分享链接：24 位 hex 一次一条活跃，可限次数与时效，兑换用条件 UPDATE 原子递增杜绝超发。移除成员是一整个事务的级联：下线其 runtime、归档绑定 agent、取消在途任务、删订阅与 daemon 令牌、删成员行，最后立刻失效成员资格缓存。

4.5资源级权限

角色之上叠加「资源属主」层——多数写操作的判据是 owner/admin ∥ 资源属主，但 agent 的调用权是唯一一处连管理员都没有豁免的地方：

资源规则
Agent 调用（触发运行）由 agent.permission_mode 决定：private 仅属主——无管理员豁免、无 agent 链路豁免；public_to 按白名单（workspace / member）。agent 调 agent 时以链顶人类发起者（originator_user_id）判权，防止借 agent 洗权限

4.6Daemon 与 Agent 身份

/api/daemon/* 使用独立的 DaemonAuth：只收 Authorization 头（结构性排除 Cookie/CSRF 问题），支持 mdt_ / mcn_ / mul_ / JWT 四条路径。实践中 daemon 主要以属主的 mul_ PAT 运行；runtime 访问经 requireDaemonRuntimeAccess 校验，且刻意用「404 = runtime 已不存在，daemon 应丢弃并重注册」作自愈信号（其余 DB 错误保持 500，防止抖动触发自清理）。

Agent 没有账号，身份是随任务生灭的 mat_ 令牌——这是全系统最精彩的安全设计：

  1. 铸造：daemon 领取任务时，服务端为每个任务铸 mat_ 令牌，绑定 task + agent + workspace + runtime 属主，24 小时过期，与领取回执同事务落库。runtime 属主缺失时取消任务而不是派发——绝不产生无主凭证。历史上曾把属主的 PAT 注入 agent 进程，此设计（MUL-2600）正是为替换它。
  2. 注入：daemon 把令牌以 MULTICA_TOKEN 环境变量交给 CLI 进程（另有 MULTICA_WORKSPACE_ID / MULTICA_AGENT_ID / MULTICA_TASK_ID 等）；daemon 侧校验注入值必须是 mat_ 前缀，CLI 侧在任务上下文里拒绝回退到用户全局配置的 token，也拒绝 login 等人类命令。
  3. 行权：请求进来后中间件覆写四个身份头并盖 X-Actor-Source: task_token；工作区解析无条件采用令牌绑定值；成员校验跑的是属主的资格——所以 agent 的能力恒等于「属主权限 ∩ 单一工作区 ∩ 24 小时」。
  4. 署名：resolveActor 据此返回 ("agent", agent_id)，评论落库为 author_type='agent'。旧路径若想声明 agent 身份，必须同时给出 X-Agent-ID 与归属该 agent 的有效 X-Task-ID——单凭 X-Agent-ID 永远不被信任，成员无法冒充 agent。

4.8攻击面加固

  • CSRF 三层：SameSite=Strict 为主防线；双提交 Cookie 的值是 nonce.HMAC(nonce, 会话JWT)——把 CSRF 令牌与会话绑定，子域写 Cookie 也伪造不了；Bearer 路径与插件 API 结构性免疫。
  • 限流（Redis 固定窗口 + Lua 原子）：send-code 5/分/IP、verify 20/分/IP、contact-sales 5/时、插件 API 120/分；邀请另有三重滑窗（发起人 10/10min · 工作区 50/24h · 收件人 6/24h，fail-closed）；X-Forwarded-For 仅在可信代理 CIDR 内采信。
  • 能力 URL 替代 Cookie：SameSite=Strict 会挡住 <img>/下载场景，于是附件下载、头像、插件面板都改用短时效 HMAC 签名 URL——凭证在链接里而不在会话里。
  • 启动守卫：生产环境下弱 JWT_SECRET 直接 os.Exit(1)；开发验证码后门在生产硬关闭；保留 slug 表解析失败则拒绝启动（92 个保留字防路由劫持）。
  • 删掉的攻击面：早期的 OpenAI 兼容透传端点 /api/llm/* 已整体移除——它曾允许任何登录用户白嫖部署方的模型密钥。
  • WS 来源校验：同源放行、X-Forwarded-Host 仅信任可信代理、其余按显式 origin 白名单。
值得留意的一处边角middleware.Auth 删除并重盖 X-Actor-Source，但不删客户端传入的 X-User-ID（认证路由会覆写，安全）；唯独公开路由 GET /api/github/setup 直接读取该头写入 GitHub 安装的 connected_by_id。它只用于「谁连接了」的展示归属、不参与任何授权判定，但属于可伪造的归属信息，重构时值得顺手收紧。
