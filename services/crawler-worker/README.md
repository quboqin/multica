# Crawler Worker

Local phase-1 credential broker worker.

It exposes:

- `POST /login-sessions`
- `GET /sessions/{token}`
- `GET /sessions/{token}/screenshot`
- `POST /sessions/{token}/input`
- `POST /crawl`
- `GET /healthz`

Run locally:

```bash
PORT=19516 \
MULTICA_API_URL=http://127.0.0.1:18080 \
DATABASE_URL='postgres://multica@127.0.0.1:15432/multica?sslmode=disable' \
node src/index.mjs
```

Cloud/self-host deployment:

```bash
CRAWLER_WORKER_REMOTE_UI=true \
CRAWLER_WORKER_PUBLIC_URL=https://your-worker.example.com \
MULTICA_API_URL=https://your-multica-api.example.com \
DATABASE_URL='postgres://...' \
BROKER_STATE_KEY="$(openssl rand -base64 32)" \
node src/index.mjs
```

With `CRAWLER_WORKER_REMOTE_UI=true`, the session URL opens a remote browser
panel. The page polls `/sessions/{token}/screenshot` and sends mouse/keyboard
events to `/sessions/{token}/input`, so a cloud worker can complete binding
without popping a browser on the server desktop. The token in the session URL is
the access credential for that panel; expose the worker only through HTTPS and
the same private/authenticated ingress as the Multica app.

By default, remote UI mode launches the login browser headless. If a connector
blocks headless Chromium, run the worker with a display-capable runtime such as
Xvfb and set `CRAWLER_WORKER_HEADLESS=false`; the same remote panel still works
because screenshots come from Playwright.

For local development, `BROKER_STATE_KEY` is optional and the worker uses a
deterministic local-dev key. Production deployments must set
`BROKER_STATE_KEY` to base64 for exactly 32 bytes.

The session page launches a Playwright Chromium browser. Sign in to the
connector in that browser, then click Complete binding on the worker session
page to capture and encrypt Playwright `storageState`. Completion fails until
the worker detects connector-owned browser state, so an empty login page cannot
accidentally activate a profile.

Successful completion returns a verification summary without secret values:

- `verification.credential_state.cookie_count`
- `verification.credential_state.origin_count`
- `verification.credential_state.domains`
- `verification.current_url`

Run `multica crawl run --connector appgrowing` with the completed profile to
verify the stored state can be replayed. This command has its own `--timeout`
budget because crawler workloads can run much longer than normal CLI/API
requests. The crawl response includes `raw.auth_probe.login_detected`; it must
be `false` for the credential to be considered usable. For AppGrowing Global,
the worker also calls the product GraphQL `userinfo` endpoint; the credential
is accepted only when `raw.auth_probe.auth_check.user_id_present` is `true`.

`capability=material_search` opens AppGrowing's material search page with the
stored browser state and captures the GraphQL material responses generated by
the page. The worker is deliberately policy-free: callers must pass
`competitors`, optional `priority_competitors`, and `selection_rules`. Agent
instructions or autopilot descriptions own business policy such as competitor
pools and weekly 40/60 selection rules. The worker returns only sanitized
selected material metadata and resource URLs, not cookies, request headers, or
raw GraphQL payloads.

Autopilots can pass the same policy as natural-language intent instead of raw
JSON:

```bash
multica crawl run \
  --connector appgrowing \
  --capability material_search \
  --timeout 5m \
  --intent-file appgrowing-weekly.md
```

The AppGrowing connector parses intent fields such as `竞品：Easycash、Kredit
Pintar`, `新素材：占比 40%，投放天数 < 7 天，曝光估算 > 1K`, and `跑量素材：占比
60%，投放天数 > 30 天，曝光估算 >= 10M` into structured `material_search`
params. It also parses common AppGrowing filters:

- `媒体：Meta Ads、AdMob、Facebook、Instagram`
- `投放地区：印尼`
- `语言：印尼语`
- `设备：Android、iOS`

These explicit filter lines map to AppGrowing's material-search query
parameters (`media`, `area`, `language`, and `platform`). Broader market
wording such as "Malaysia fintech competitors" should be interpreted by the
agent before calling the worker; the worker itself should not guess business
intent from arbitrary prose. Unknown media names are preserved as `media_names`,
so a caller can surface that the name could not be mapped instead of silently
dropping the user's filter. The result rows include `asset_type`, `preview_url`,
media/platform/area/language labels, and resource URLs so the agent can render a
filterable HTML attachment with inline image/video previews.

It also accepts per-competitor AppGrowing leaflet URLs, for example `Easycash
品牌页：https://appgrowing-global.youcloud.com/.../leaflet`. Explicit
`--params-json` values override parsed intent values. Parsed filters are applied
to both generated search URLs and per-competitor leaflet URLs.

AppGrowing Global rejects the replay probe in headless Chromium in local
testing, returning HTTP 406 from `userinfo`. The worker therefore runs this
connector's crawl probe in headed Chromium by default. Server deployments need
a display-capable runtime such as Xvfb, or an equivalent remote-browser setup.

## Declarative connectors

The API and worker can share additional deployment-reviewed connector manifests
through `MULTICA_CREDENTIAL_CONNECTORS_JSON`. Declarative connectors support
credential binding, `profile_verify`, and constrained `page_extract` recipes
without rebuilding the images. A recipe may use click/fill/select/wait/press/
scroll steps and extract text or href/src/title/alt/value attributes.

This is not an arbitrary-code plugin mechanism. Target URLs must stay inside the
connector's declared target domains, and the worker never evaluates JavaScript
from a task. Site-specific GraphQL schemas, anti-bot handling, or custom result
normalization still belong in a reviewed connector capability. See
`docs/creative-material-workflow.md` for the manifest shape and deployment
requirements.
